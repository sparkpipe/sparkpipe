## THE DESIGN (ledger D2 plan completion — written before coding)

The ledger's D2 entry is one line; this is the missing loop-level
design, derived from the code.

### The defect (P1's serving-loop half)

`SparkModelResidentdProgressRoutes` (node/model_residentd.c) bounds the
resident to **at most one adapter-capable operation per Progress
pass** across ALL routes (`adapter_submitted` stops the ring scan at
the first success — adapter submit OR continuation prepare). The
resident run loop Progresses at most once per poll wakeup (10 ms cap
with active routes). Net: a committed, device-ready route waits ~a
full loop pass per frame regardless of adapter capability; K ready
frames drain at one frame per wakeup. The adapter's own admission
control (`max_inflight_submission_count`, enforced by submit returning
BUSY) is never consulted — the loop serializes BEFORE the adapter can
speak. For the dsv4 Rosetta Stone shape (device-resident chain + async
completion, 8 tok/submission) this bound defeats the chain: the loop
feeds one frame per wakeup no matter how deep the device pipeline is.
This is PATTERN B verbatim: the loop is the bubble.

### The redesign (structural, three surfaces)

1. **node/model_residentd.c — adapter admission follows the adapter
   contract.** The one-op-per-pass bound applies ONLY to adapters
   without `SPARK_MODEL_SERVING_ADAPTER_CAPABILITY_ASYNC_COMPLETION`
   (submit blocks until the frame completes; interleaving transport
   service between frames is load-bearing there — qwen families until
   their P1 port). Async adapters drain the committed FIFO every
   Progress: the ring scan continues past successful submits and stops
   only when the adapter refuses (BUSY = its declared backpressure) or
   the ring completes. FCFS head order is untouched — only the
   committed-FIFO head ever submits (existing gate, kept verbatim);
   draining just means the head advances within the same pass instead
   of across poll wakeups. The ADMIT-FIRST phase order inside Progress
   is untouched.

2. **runtime/model_resident_client.c — submitted means on the wire.**
   `SubmitKind` (prepare/continue/submit) and `QueueDecision`
   (commit/abort) flush the outgoing queue before returning. The flush
   is the existing non-blocking send loop; EAGAIN leaves bytes queued
   for Progress/poll-write exactly as today. Progress becomes a pure
   drain+advance. This is the client-side half of the same defect: a
   submission built in step N reached the resident only at step N+1's
   Progress, which is why the engine carried a compensating patch.

3. **runtime/model_batch_engine.c — delete the bubble patch.** The
   trailing extra `SparkModelPipelineClientProgress` in
   `SparkModelBatchEngineProgress` ("Flush the just-queued
   submission(s) immediately ... removing a one-iteration bubble") is
   redundant by construction under (2): every dispatch and every
   commit decision is already on the wire when the dispatch loop ends.
   The step loop becomes: drain -> dispatch. One loop, no patches.

What is deliberately NOT here (scope discipline):
- No admission-policy change in the batch engine (contbatch2's lane).
- No per-family module edits (P1's module half is fleet-gated).
- The 10 ms resident poll cap and the wake function stay as-is; the
  adapter wake already breaks idle waits.

### Host oracle (before touching, per ledger PATTERN C discipline)

New `tests/test_steploop_admission.c` on the existing harness pieces
(real residentd x3 ranks + the async chain fixture adapter + batch
engine): N one-token requests against a deployment sized so the whole
batch is admitted at once; measure the client-side Progress calls from
first dispatch to full drain, and the completion coalescing per call.
- PRE-fix floor: measured against unmodified code; the serialized
  bound forces ~one completion per round trip, so the drain needs many
  Progress calls. Receipt recorded in this report.
- POST-fix ceiling: pinned below the measured post-fix drain with
  margin; the pre-fix code must exceed it (the test discriminates).
- FIFO order: token emission stays oldest-first under the drain
  (already pinned by TestModelBatchEngine* asserts; re-pinned here at
  depth).
All existing suites must stay green unchanged (outcome-based).

## Receipts

### The oracle discriminates (tests/test_steploop_admission.c)

Real 3-rank residentd topology + the serving fixture adapter in its new
hold-completion mode (submit enqueues, progress releases — the async
shape the fixture's ASYNC_COMPLETION capability declares), 4 one-lane
requests = a committed FIFO of depth 4 on the resident.

- PRE-fix (one-adapter-op-per-pass bound in force): resident exit
  receipt `model_residentd_exit rank=0 stage=0 passes=… adapter_ops=…
  max_ops_per_pass=1` — exactly one adapter op per Progress pass on
  every rank; the test's `>= 2` assertion fires. Receipt in
  /tmp/prefix_run.log (lane session; the run's own stderr captured the receipt).
- POST-fix (adapter-contract admission): `max_ops_per_pass=4` on all
  three ranks (repeat runs: 4/4/4, then 4/2/2 with commit arrival
  jitter — always >1), drain stable at 6 client Progress calls.
  The committed FIFO drains within one pass; only the adapter's own
  BUSY can throttle admission now.
- FIFO order preserved: token emission asserted oldest-first
  (token_request_ids[i] == 5100+i).

The drain-calls metric alone does NOT discriminate (the completion wake
chain re-feeds the loop even pre-fix, so round trips stay ~6) — the
pinned invariant is the ops-per-pass receipt, which is the quantity the
ledger's defect class is about: frames admitted per serving-loop pass.

### Fixture fidelity note

The fixture adapter declared ASYNC_COMPLETION while completing inline
inside submit — it could never exercise the async contract. The new
hold mode is opt-in via a NEW config file
(tests/fixtures/model_serving_adapter_config_hold.json,
"hold_completion_steps": 2); the shared default config is untouched, so
every existing suite sees byte-identical inline behavior. Additive
fixture change only (tests/ excluded from the ratchet by construction).

### Behavior preserved for sync-submit adapters

Adapters without ASYNC_COMPLETION (the pre-port qwen families) keep the
one-adapter-op-per-pass interleave. One deliberate improvement applies
to them too: the old loop aborted the ENTIRE ring scan after the first
adapter op, so other routes' transport posting and completion finishing
were skipped for that pass; the redesigned scan always walks the full
ring and gates only adapter operations. Route state transitions are
per-route and mutex-guarded, so ordering is unchanged. The committed-
FIFO head gate (only the head ever submits) is untouched — FCFS
adapter admission holds under the drain.
