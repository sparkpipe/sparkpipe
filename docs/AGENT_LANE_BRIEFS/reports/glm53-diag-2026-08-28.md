## 5. The guilty site — ranked read

### GUILTY (new, evidence-converged): persistent-receive template is
### registered from the WRONG CREDIT-BINDING ROW for tree step 2 under
### TP16 — RouteBinding inconsistency inside tp_device_collective.c

- `SparkTpDeviceCollectiveRegisterCredits` registers each step's
  persistent-receive template from `bindings[RouteBinding(step)][credit]`
  (tp_device_collective.c:2819-2822). `RouteBinding` (tp_device_collective.c
  :319-328) maps step 2 -> binding row 1 whenever
  `binding_route_count != SPARK_TP_DEVICE_COLLECTIVE_DIRECT_ALL_TO_ALL_PEER_COUNT(3)`
  (SPLIT_RING_ROUTE_INDEX == 2, include/sparkpipe/spark_tp_device_collective.h:16).
- Tree operations build their per-op packet from `bindings[step_index]`
  RAW (tp_device_collective.c:1103 — no RouteBinding; only
  BuildRingPackets at :1058 applies the remap).
- For TP16 the partner tree has 4 steps (XOR 1,2,4,8) so
  binding_route_count = 4 != 3 and step 2 (the XOR-4 partner, route
  `.2.<remote>.<local>` — exactly the route in every failure line)
  diverges: template from row 1, packet from row 2.
- The module's credit bindings are laid out route-major with one row =
  credit_count x credit_bytes (module
  spark_glm5_next_resident_decode_stage_module.c, binding loop). Numbers
  from the deployed config (spark0 config/stage.json):
  `execution_row_capacity=16` (= max_active_sequence_count), hidden 4096,
  bf16 2 B -> credit_bytes = 16x4096x2 = 131072 B; credit_count =
  pipeline_slot_count(4, "inflight=4" in the ready line) x
  CREDITS_PER_SLOT(2) = 8. One binding row = 8 x 128 KiB = **0x100000
  (1 MiB)** — exactly the observed template/packet delta on every rank.
- The rejection site: `SparkHiddenSparkHostRdmaActivatePersistentReceive`
  (rdma.cu:4753) compares the packet against the registered template
  (rdma.cu:4775-4784: hidden_bf16 / sideband_payload / sideband_kind /
  sideband_bytes_per_sequence must all match) and returns
  SPARK_STATUS_INVALID_ARGUMENT — the instrument print's four value
  pairs are exactly these four fields; side/kind/bps match, hidden is
  off by one row.
- Propagation (all local, matches every log):
  ReserveOperation marks the op failed (tp_device_collective.c:2162-2167)
  -> PublishCompletion delivers status 1 (tp_device_collective.c:2516-2534)
  -> module TpCompletion prints `status 1 ... rows 0` (the "rows 0" is
  the probe's own literal 0 — lane module prints `(unsigned long long)0u`
  for rows; chainfail shows the true rows 1) -> chainfail stage 1 layer 0
  -> route_failed reason=2 -> run=invalid_argument -> API status 4, no
  tokens.
- Why no wire traffic: sends only start after ALL steps' resources are
  reserved (tp_device_collective.c:2170-2183); reservation aborts at the
  step-2 mismatch, so doorbell_sends=0 everywhere.
- Why glm52 TP8 and DSV4 Flash TP4 never hit it: TP8 has 3 steps ->
  binding_route_count == 3 == PEER_COUNT -> RouteBinding is the identity
  for every index; TP4 has 2 steps (indices 0,1 — never 2). glm53 TP16
  is the first 4-step topology in the fleet. (K3's planned TP16 will hit
  the same wall.)

### EXONERATED (this run's direct evidence)

1. **Unhandled control message type in PumpControl's final else /
   HELLO (rdma.cu ~3069-3075):** the final else DOES report
   (`SparkHiddenSparkHostRdmaReportControlError`) and debug_enabled=1 is
   proven live — a single unknown control message on ANY rank would have
   printed `hidden_spark_rdma_control_error ... type=N`. All 16 ranks:
   zero. Plus control_busy=0 and no sends — no control traffic existed.
2. **Credit repost vs MAX_PENDING_RECEIVE_COUNT:** the op never reached
   receive activity (nothing sent, nothing to repost); the counters and
   the single activate-template line place the failure at FIRST
   activation of the first op (ordinal 0).
3. **Completion struct unfilled -> rows-0:** the module's "rows 0" is a
   print artifact (hardcoded 0u at the probe site); the completion's
   status field was decisively filled (1) and correctly propagated.

### Fix shape (coordinator's write set — NOT changed by this lane)

Align the two indexings. Making the tree op-build use RouteBinding would
alias tree steps 1 and 2 onto one buffer row (wrong data, concurrent
use) — the consistent direction is either registering templates with the
raw step index for tree algorithms (per-algorithm template mapping), or
giving the ring its own binding rows so RouteBinding's aliasing
disappears. The module's 4-row layout already allocates one row per
route, so the ring-aliasing looks like the leftover.
