## Family 1 — glm52 (commits 998b179 + efe69fb, rebased)

### Module lifecycle onto the shared library
The five pasted entry-point shells (ABI validation, calloc, ledger tag,
counter init, destroy-on-failed-prepare, quiesce-then-teardown destroy,
snapshot base) become ops hooks on `SparkStageModuleLifecycle`; behavior

`state_prepare` now receives the `SparkFirmwareModuleConfiguration` the
lifecycle already validated — glm52's configure cross-checks
`configuration->model_revision` against the node context, which the old
hook signature could not see. qwen38_27b and dsv4 prepare hooks take the
extra parameter and ignore it (mechanical, both families' builds green).

## Family 2 — k3 (commit be122ff)

k3's serving adapter is NOT the pasted shape the template replaces; the
cutover takes only what is genuinely shared:
- descriptor identity block onto
  `SPARK_SERVING_ADAPTER_DESCRIPTOR_IDENTITY` (five identity strings +
  ABI pair, byte-identical values).
- memory-M1 rides the template: the per-submit host arrays and device
  twins are typed `SparkMemoryBuffer`s; the six pasted cudaMemcpy pairs
  become space-aware copies (the pasted submits ignored copy errors —
  unchanged), same allocators, same failure statuses (CAPACITY_EXCEEDED).
- the descriptor/snapshot/completion/interface bytes constants replace
  equivalent inline sizeof casts.

Two template legs deliberately do NOT apply (documented in-file):
- capability chain: the base carries DRIVER_OWNS_KV, which k3 must NOT
  declare — its slot-reuse contract is NONE and the shared descriptor
  validator pins the pair together (runtime/model_serving_adapter.c:59).
  The flag list stays family-side: the DRY law working, not an
  un-migrated paste.
- tp_collective parser: k3's host-TCP tier parses a different schema
  (peers as host:port strings + the optional device_collective object),
  and there is no LoadDriver/reserve spine (the runner is built in,
  submissions complete synchronously). Forcing the template's schema
  here would have changed the config contract — refused.

Consequence for the family count: k3 is a full serving-adapter family
with no adapter paste; its dup_report footprint was already zero. There
is no k3 module-lifecycle cutover either — SparkK3ModuleInitialize/Destroy
is a bind/pack API, not a SparkFirmwareModule (no five ABI entry points),
so the lifecycle library does not apply. "5/5" by the honest count:
27b, dsv4, glm52 on the libraries; k3 verified paste-free; glm5_next the
last real cutover (below).
