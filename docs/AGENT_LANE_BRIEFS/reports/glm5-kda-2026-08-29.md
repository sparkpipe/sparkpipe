## R3 — the root cause: the residual streams multiplied by tp_degree EVERY layer

The hidden stream surface grows x~16 per layer from layer 0 (element 0,
bf16-decoded, rank 0):

    L0 0.0055 -> L1 0.086 (x15.6) -> L2 1.98 (x22) -> L3 28.6 -> L4 399
    ... -> L16 ~1e17 -> L17 ~1e18

Mechanism: `Glm5NextHcPostKernel` adds the rank-REPLICATED residual term
`comb @ snapshot` on every rank, and the chain's only per-layer streams
reduce (the HC-wide twin) then SUMS the streams across 16 ranks: the
residual is multiplied by tp_degree once per layer. Meanwhile the narrow
attention reduce's result was never consumed (HcPost ran before it, on
each rank's local partial; for KDA it even reduced the head-space scratch
instead of the full-width partial), so each rank's streams also carried
only its own 1/16 attention contribution into the MLP site. The x16/layer
explosion reaches bf16 INF at layer ~34 — exactly the prior lane's
"-0.0 at layer 34" landscape. The M3 validator could not see any of
this: at tp_degree=1 the wide reduce no-ops and both layouts coincide.

## R6 — the SECOND defect: the packer shards fused tensors on the wrong axis

With zeros gone, generation is degenerate (one token repeated; on a real
372-token COMPSEC prompt the per-position argmax runs 101108 -> 19607 ->
55683 -> 91016 -> 18446 -> 25514 -> 15074 in ~90-token runs; decoded
pieces are semantically unrelated to the prompt: "bu", "PIN", "Fed",
" MI", "itos", "atable"). Magnitude probes show KDA sublayer partials
~1e-3 against streams ~O(1): the KDA layers contribute almost nothing.

Root cause, in tools/glm5_next_resident_stagepack.py (fixed, 1dac68b):
`add_fused_rows` slices the CONCATENATED q|k|v|beta rows contiguously
(`fused[s0:s1]` over 24640 rows), so rank r ships global fused rows
[r*1540,(r+1)*1540). Rank 0's sections become q_proj[0:512] (accidentally
right), q_proj[512:1024] as "k", q_proj[1024:1536] as "v", q_proj[1536:
1540] as "beta"; ranks >= 1 straddle section boundaries. The format
docstring already specified the correct contract ("Row sharding slices
every section by whole rows") and the module's split kernel + per-head
kernels index LOCAL head ids per section — packer and kernel disagreed.
`add_up_gate_fused` had the same defect for [up | gate] (dense MLPs on
layers 0-2 + the shared expert). Both layouts are identical at TP1,
which is why the M3 gates and the module loader (expected shape =
total/tp) never saw it.

Packer fix is committed; a rank-0 rebuild with the fixed packer was
running at session end (ceph-read-bound, ~5+ h: /home/spark0/
glm53_packs_fixed/glm5_next_stage.tp16.rank0.g5nsp; dry-plan = 1160
tensors, exactly the deployed pack's inventory). Offline verification
before fleet redeploy:

    pack L17 kda_qkv_beta rows[0:512]   == ckpt q_proj[0:512]
    pack L17 kda_qkv_beta rows[512:1024] == ckpt k_proj[0:512]
    pack L17 kda_qkv_beta rows[1024:1536] == ckpt v_proj[0:512]
    pack L17 kda_qkv_beta rows[1536:1540] == ckpt b_proj[0:4]
    (same for decay_gate_down f|g and dense/shared up|gate)

Checked and found CORRECT (no action): deployed pack attn_norm/o_norm/
conv weights match the checkpoint byte-for-byte at layers 0/16/17 (the
o_norm "alternating zeros" I flagged mid-session was my analysis script
misaligning f32s — the hexdump shows exact F32 upcasts).
