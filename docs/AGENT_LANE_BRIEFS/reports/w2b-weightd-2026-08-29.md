## What landed (1 commit)

1. `runtime/spark_weightd.c` (+198 net) — VMM truth:
   - Arena = ONE `cuMemAddressReserve` virtual span (stable for the arena's
     whole life) carrying independent `cuMemCreate` physical chunks at the
     driver's RECOMMENDED granularity, never below the design's 2 MiB page
     law and always a multiple of the granularity, mapped one by one with
     `cuMemMap` and made read-write with `cuMemSetAccess` for the load copy.
   - Physical chunks are tracked individually in the arena (`chunk_handles`),
     so a later tier can attach/detach physical pages — or export them
     `CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR` for a consumer's
     `cuMemImportFromShareableHandle` + read-only `cuMemMap` — without
     moving the base or copying a byte. Free is exact-teardown:
     `cuMemUnmap` the span, release every chunk, `cuMemAddressFree`.
   - THE CONTRACT IS UNTOUCHED: identity canonicalization, the wire
     protocol, connection-scoped refcounts, consumer-death reaping,
     cold retention, the NO-2x gate (reclaim cold-only, fail
     CAPACITY_EXCEEDED with nothing allocated), and the TERM path are the
     merged W2a code — all five W2a contract tests pass UNCHANGED over the
     VMM path.
   - The daemon still sets its own mapping RW (the load writes through it);
     consumer maps are the read-only side of the staged fd tier.
2. `tests/cuda_stub/cuda.h` (new) + `cuda_runtime_stub.c` (+260) — the
   minimal cuMem* surface the daemon uses, names/values mirroring the real
   driver API so the same source compiles against real `<cuda.h>` on GPU.
   The stub models the physical/virtual split faithfully enough to catch
   lifecycle bugs: a physical chunk is a small tracked record; a virtual
   reservation is a tracked real allocation of the full span (so mapped
   reads/writes touch real bytes — the attach test compares pack bytes
   through the mapped pointer); map/unmap enforce exact (pointer, bytes)
   pairs; `cuMemRelease`/`cuMemAddressFree` refuse while anything is still
   mapped. Both records ride the tracked allocator, so the tests'
   zero-outstanding-allocs check covers the VMM path. `cudaGetDevice`
   joins the runtime stub.
3. `runtime/spark_weightd_attach.c` + `include/sparkpipe/spark_weightd_attach.h`
   (new, +307) — the serving-side attach surface over the deadline-client:
   - Kill-switch parity with the W1 pipeline env-off pattern:
     `SPARK_WEIGHTD_SOCKET` set (non-empty) requests an attach;
     `SPARK_WEIGHTD_ATTACH=0` forces off even then; unset socket = today's
     direct load (the default, zero-risk).
   - The identity is PUBLISHED BY THE DEPLOYMENT, never computed per
     process: `SPARK_WEIGHTD_PACK_SHA256` (required — without it there is
     no identity and the helper declines), `SPARK_WEIGHTD_IDENTITY_MODEL` /
     `_REVISION` overriding the caller's family defaults; topology +
     geometry fingerprint + pack_bytes come from the caller (the module
     folds its pack header geometry and passes the tp configuration hash).
     Rationale: a consumer-side full-pack hash would re-read the bytes the
     daemon exists to stop re-reading — the sub-second warm code-redeploy
     attach is the design's headline win.
   - Unconditional fallback contract: env_off / no_socket / no_identity /
     identity (malformed) / no_daemon (refused connect — the front-door
     fail-closed) / deadline or daemon-death mid-exchange (status-named) /
     the daemon's refusal (HASH_MISMATCH, INVALID_ARGUMENT, ...) — every
     "not attached" returns OK with client==0 and a bounded reason string;
     the caller proceeds with its direct pack load. The daemon stays the
     bytes authority (digest verified before any arena exists), so a stale
     or lying deployment identity can only fall back, never serve wrong
     bytes.
   - `SparkWeightdAttachRelease` closes WITHOUT detaching: the daemon reaps
     the dead socket, drops the reference, and the arena stays warm — the
     crash path and the clean teardown are one code path.
4. `modules/dsv4_resident_decode_stage/source/spark_dsv4_resident_decode_
   stage_module.c` (+141) — the first real consumer. `SparkDsv4ModuleLoadPack`
   attempts the attach after the geometry check and before the load; on
   success the per-tensor load BINDS BORROWED SLICES straight out of the
   arena at their pack offsets — the arena IS the verified pack image: no
   per-tensor allocation, no copy, the pointer IS the weight, and the
   ledger records nothing it would free (the bytes are daemon-owned).
   `SparkDsv4ModuleValidateEntry` already bounds every offset against
   file_bytes and the attach proved `arena_bytes == file_bytes` (a size
   disagreement falls back with `arena_mismatch`). The load pipeline is
   skipped when attached (nothing to pipeline); coverage validation and
   binds run identically. Teardown closes the client and zeroes the
   borrowed pointers. Env-off is silent; every other fallback logs one
   `weightd_fallback reason=...` line; a successful attach logs
   `weightd_attach warm=%u generation=%llu bytes=%llu`. NO-2x on the node:
   attached serving holds NO second copy of the weights.
5. Build wiring: `sources.mk` moves `runtime/spark_weightd.c` into
   `$(SPARKPIPE_RUNTIME_SOURCES)` and adds `spark_weightd_attach.c` (the
   one-line addition the W2a author anticipated — the client is now every
   consumer's import surface); `Makefile` links the daemon and both weightd
   tests against `$(RUNTIME_LIBRARY)` (no duplicate symbols), compiles the
   two weightd objects with the model-common include shape (real CUDA
   headers where CUDA_HOME exists, the stub where it does not), adds
   `SPARKPIPE_CUDA_DRIVER_LINK` (-lcuda on GPU; the daemon needs the driver
   surface; k3's module rule already set this precedent), and registers
   `test_weightd_attach`.
6. `tests/test_weightd_attach.c` (new, tests/ — excluded from the ratchet):
   the fallback matrix + the warm-hit proofs, cuda-stub, server in-process.
7. `tools/sparkpipe_weightd_vmm_verify.sh` (new) — the STAGED GPU receipt
   for the real VMM path (spark-gated, never run offline, skips itself
   without CUDA_HOME + nvidia-smi): builds a consumer against real
   cudart+libcuda and proves on hardware: recommended granularity >= 2 MiB;
   cold attach maps a real span whose bytes equal the pack bytes (D2H
   readback through the mapped VA); warm attach shares one handle at
   refcount 2; teardown frees every chunk + the VA (driver orderings hold).
8. `include/sparkpipe/spark_weightd.h` — header comments updated from the
   W2a stand-in note to the W2b truth (no API/surface change).

## Design notes / honest limits (for the reviewer and the fd-tier lane)

- `device_handle` in ATTACH_RESULT still names the DAEMON's pid-local VMM
  mapping — it means nothing in another process until the POSIX-fd export
  tier (SCM_RIGHTS side-channel or an ABI-bumped frame) plus the consumer
  `cuMemImportFromShareableHandle` + read-only `cuMemMap` land. The W2b
  consumer therefore serves from the arena correctly ONLY when the consumer
  shares the daemon's address space (the host-stub truth) — on GPU the
  attached-binding module path is gated on that tier's receipt, staged as
  `tools/sparkpipe_weightd_vmm_verify.sh`. The identity/refcount/fallback
  semantics exercised here are exactly what the fd tier rides on.
- The 110 GiB ceiling still counts CLAIMED arena bytes (the identity's
  arena_bytes), not the granularity-rounded physical span; at 2 MiB chunks
  the rounding slack is <= 2 MiB per arena (<= 32 MiB across all 16) —
  noise against the law, but worth counting physically if ceilings ever
  get tight.
- A 100 GiB arena at 2 MiB chunks is ~51k `cuMemCreate`+`cuMemMap` pairs —
  a one-time cold-path cost (driver calls, microseconds each); the design's
  alternative (fewer, larger chunks) trades against the TLB law. Measured
  properly only by the GPU receipt.
- The consumer's identity digest is env-published (`SPARK_WEIGHTD_PACK_SHA256`);
  deployments that don't publish it get today's direct load (correct, just
  not warm). The registrar/pack tooling already publishes SHA256SUMS, so
  the wave tools can export the digest at launch (W3).
- dsv4-module link note for the node firmware build: the module now
  references `SparkWeightdAttach*`/`SparkWeightdClient*`, which live in
  `$(RUNTIME_LIBRARY)` (plus `-lcuda` transitively via the daemon core) —
  the k3 module rule already links exactly this set.
- Cross-run interference seen during gating (not this lane's defect):
  concurrent lanes' `make offline-gates` collide on the registrar test's
  fixed PORT_BASE (EADDRINUSE) and on /tmp release-agent dirs; the
  coordinator is landing per-run unique ports. Base 5e3e22e verified green
  standalone between collisions; my final gates run is the clean one above.
