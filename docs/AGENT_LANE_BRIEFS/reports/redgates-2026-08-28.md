### Diagnosis: REAL REGRESSION, not a stale expectation (commit cited)

`f0bd7c8` ("serving-adapter template + memory-M1 handles; qwen38_27b +
dsv4 cut over") introduced `SparkServingAdapterTemplateReservePending`.
Its header documents: "the family pending struct embeds
SparkServingAdapterPendingCommon (**after any owner pointer** the family
fills itself)" — but the implementation wrote the common view at
**element offset 0**, 8 bytes early for every family (all four pending
structs start with an 8-byte `owner` pointer). Every common field read
back shifted one slot; worst of all the free-slot scan read the owner
pointer as the `active` flag, so pipeline slots leaked → BUSY.

Instrumented completion match (temporary print, reverted before commit)
made the shift visible — the completion echoes the frame's request_id 9,
the pending's misaligned "request_id" holds sequence_id 100:

```
RGDIAG completion req=9/100 seq=100/100 pos=0/0 prog=1/1 matches=0
qwen38_27b_debug frame_status status=6 prefill=0 rows=2
```

The commit's own message flagged the missing validation: "full test
matrix runs on spark5 before merge" — that run never happened on the
mac path.

**Fix (commit `5d4a77d`):** add the `common_offset` parameter — family
layout as data, exactly like the existing `last_row_by_lane_offset` —
and pass `offsetof(family, common)` from the three call sites
(qwen38_27b, dsv4, glm52). Header comment now states the offset
contract.
