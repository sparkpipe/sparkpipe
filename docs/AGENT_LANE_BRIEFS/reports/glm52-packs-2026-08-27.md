## Sources and precision policy (the load-bearing finding)

The brief said "GLM-5.2-FP8, 704G, 141 shards, complete" and the in-tree
packer (`tools/glm52_resident_stagepack.py`, commit 10033c8) wanted TWO
sources: a BF16 master spine (`zai-org/GLM-5.2 @ b4734de4`) plus the FP8
checkpoint for routed experts. The BF16 master DOES NOT EXIST in local
storage any more:

```
$ ls /mnt/cold-raid6/22tb0/models/hf/zai-org/   # on spark0
GLM-5.1
GLM-5.1-FP8
GLM-5.2-FP8        # <- the only 5.2 source; the NVFP4 copy is gone too
$ ls /mnt/model-warm
deepseek-v4-flash  deepseek-v4-pro-0813-ga  glm-5.3-flash  kimi-k3  packbuild  qwen3.8-flash-next
```

Census of the FP8 checkpoint (from headers, via the index): EVERY linear
weight is F8_E4M3 with an F32 `weight_scale_inv` tile — attention
(q_a/q_b/kv_a/kv_b/o_proj), indexer wq_b/wk, dense MLP (layers 0-2), shared
experts, routed experts. Only these stay high precision: `embed_tokens`,
`lm_head`, all layernorms + indexer k_norm (BF16), router `gate.weight`
(BF16), `e_score_correction_bias` (F32), indexer `weights_proj` (BF16).

So the packer was rebuilt (commit 1138e00, 4afb9b2) to restore the ORIGINAL
precision policy (95c3e3b): spine linears dequantize at pack time

    bf16(w[i,j]) = bf16(f32(fp8_code[i,j]) * scale_inv[i//128, j//128])

(128x128 blocks, ties-to-even, NaN-canonicalizing), BF16 tensors pass
through byte-exact, routed experts copy fp8 bytes verbatim with row-expanded
F32 scales — all producing the UNCHANGED v3 wire format (CODEC_BF16 spine /
CODEC_FP8 experts), so the serving kernel path and the module are untouched.
Provenance of exact pack bytes: `pack_recipe_sha256` ("fp8-dequant-128x128-
blockwise") + `source_config_sha256` (records the source dir) in each pack
header, plus a per-pack receipt (below). MODEL_REVISION stays
b4734de4... because the firmware description (outside this lane's write
set) pins it and the module/adapter compare it end to end.

Two runtime consequences:
  1. The packer is numpy-only now (no torch, no safetensors) — nothing on
     the sparks has torch; spark0 has numpy 1.26.4.
  2. Partial quantization blocks exist: kv_a_proj_with_mqa is [576, 6144]
     (4.5 blocks) and its scale tile is ceil-shaped [5, 48]. The first
     real-source build caught this (strict shape check failed closed);
     fixed in 4afb9b2 with a regression test.

## P3 Build — PLAN CHANGED (deviation noted)

Original plan: rank-0 build -> verifier PASS -> lockstep all-ranks pass.
The first rank-0 attempt found the partial-block scale shape (good - the
strict check did its job). After the fix, spark0's RAID6 was saturated by a
DSV4-lane pack job (same array), collapsing my read rate to ~3-40 MB/s;
a two-pass plan (1.5x source reads) would have taken many hours. I merged
the phases into ONE lockstep `--all-ranks` pass and moved the verifier gate:
validator PASS on rank 0 is required BEFORE any deployment (the only
consumer of the packs), not before building ranks 1-7. The slicing logic is
