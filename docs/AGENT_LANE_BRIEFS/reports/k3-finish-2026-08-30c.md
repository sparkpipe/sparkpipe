## 2. THE FLEET-BLOCKING ADAPTER DEFECT (found + fixed this session)

Symptom: the 20:06Z wave launched all 16 ranks; every one logged
`model_residentd initialize=invalid_argument status=1
phase=adapter_initialize` and exited. Uniform across ranks/stages.

Root cause (modules/k3_resident_decode_stage/source/
spark_k3_serving_adapter.c, K3ServingLoadConfiguration): the loader
parsed `tp_collective` ONLY when `device_collective` was ABSENT, but
`SparkK3StageRunnerInitialize` unconditionally creates the host TCP
collective at `tp_degree > 1` and returns INVALID_ARGUMENT on a null
`tp_collective`. Every TP4xPP4 fleet config carries the NCCL
device_collective → null host config → 16/16 init death.

Why now: the path had NEVER been exercised — the on-node smoke
(k3_smoke_rank0.sh) always ran tp_degree 1 / world_size 1 (the derive
path, no collective), and the fleet configs were only ever file-verified.

Evidence chain (all on sparke, adapter smoke fed the FLEET config):
- fleet config as deployed (tp_degree 4, world 16, NCCL device tier,
  kv_pages 64): `INIT FAIL 1` — REPRODUCED.
- A/B: kv_pages 2 → still FAIL 1 (NOT the kv_pages change).
- isolation: no collectives → FAIL 6 (loader cap), tp_collective only →
  FAIL 4 (host connect), device only → FAIL 1 (the null host config).
- after the one-line fix: `sparkpipe_k3: creating host collective tp=4
  rank=0 port=61620` → create proceeds to its connect stage (IO_ERROR
  against a dead peer on the smoke node — expected; on the fleet all 16
  come up in one wave and the connects succeed).

Fix: parse `tp_collective` for EVERY `tp_degree > 1` (comment documents
the live receipt). Ratchet 228826 → 228830 exact (+4). The fixed
`libk3_serving_adapter.so` (2,956,408 B, built from this commit's source)
is staged to all 16 runtime trees. `make offline-gates` PASS.

- GOTCHA (live-verified): the slice requires `--pp1` — the PP4 stage
  tables VALIDATION_FAIL a 0_4 pack (`INIT FAIL 9`); `--pp1` derives the
  bounds from the pack manifest. Also `--dump` is position-sensitive
  (argv[2]).
- The tool's Σ-ranks mode is structurally inapplicable across 4
  LN-interleaved layers: at tp1 the rank dumps carry UNREDUCED partials
  through per-layer RMSNorm/swish/softmax (nonlinear in the sum), so
  `full[k] ≈ Σ rank[k]` cannot hold (observed worst rel 1.97 — the mode
  is calibrated for ONE linear segment, i.e. the dump point of a single
  GEMM block).

  localhost step-xor collective, post-all-reduce dumps) is the right
  instrument: the four dumps are BIT-IDENTICAL to each other (the
  collective is deterministic), and vs the tp1 full-slice dump:
  **103/7168 columns beyond the 0.03 line, worst rel 0.0469**, all
  abs deltas ≤ ~0.012 (≈3-5 BF16 ulp at the checker's 0.25 scale);
  98.6% of columns inside tolerance. This is the documented
  BF16-partial-sum effect AMPLIFIED ACROSS 4 LAYERS — the 0.03 line is
  calibrated per-layer. The committed verdict stands FAIL at 0.03 and is
  reported as such; the clean PASS instrument is a 1-layer slice
