## R1 — B1 routes to the certified screened head

**Before:** `SparkLmHostLaunchHeadScreenedArgmaxWithScore`
(model-families/common/include/sparkpipe/spark_lm_kernels.cuh) short-
circuits `row_count==1` to `SparkLmHostLaunchHeadDirectArgmaxWithScore`
— the full-vocabulary BF16 rescore. The qwen38 27B module's decode head,
prefill final-position head, and MTP argmax row all go through it, so
every B1 token read the whole BF16 head shard.

**After (dispatch-only, module level):** those one-row call sites now
route to `SparkLmHostLaunchHeadCertifiedFp8B1WithScore` — the certified
screened head DSV4 already ships (FP8 shadow scan with round-up
certified bounds + exact BF16 rescore of the candidate set). The
certified shadow is quantized once at head-shadow time; slots grow the
candidate buffer to the full rank-local vocabulary (the certified
screen's "full B1 rank-local candidate capacity" contract).

**The common launcher's B1 branch is UNTOUCHED** — it is pinned by
tests/test_dsv4_native_compute_source.py ("B1 direct exact-head
dispatch" / "B1 skips overflowing shadow screen"); both gates re-ran
green. The certification gates were not weakened anywhere; the
`forbid`/`require` contract on the certified kernels re-ran PASS.

## R5 — immutable validation hoisted off the per-submission path

`SparkModelServingAdapterValidateRuntimeSubmission` re-ran the
(descriptor, limits) pair — the 12-check DESCRIPTOR_CHECKS array plus
the limits chain — at EVERY layer of EVERY submission (pipeline client,
resident client per rank, residentd x2, adapter chain; the dsv4 adapter
alone re-validates 3x per submit through prefetch/resolve/submit). The
pair is immutable per component and is already validated at configure.

New `SparkModelServingAdapterValidateRuntimeSubmissionPrevalidated`
(runtime/model_serving_adapter.c) runs the identical per-submission
field/capacity/row checks minus the immutable part; null-argument
statuses match ValidateRuntimeLimits's. Call sites switched: pipeline
client submit (+ pair validation added once at initialize), resident
client submit/continue, residentd x3, dsv4 + qwen38_27b adapters.
Fail-loud contract asserted in `tools/perf_r5_validate_timing.c`:
identical statuses on valid / capacity-exceeded / field-invalid.

Receipt (spark5 CPU, decode bucket 8 lanes/8 rows):
```
parity valid          : full=0 pre=0 OK
parity capacity       : full=2 pre=2 OK
parity field-invalid  : full=2 pre=2 -> full=1 pre=1 OK
timing full    309.0 ns / submission
timing pre     255.4 ns / submission
hoisted per call        53.6 ns (1.21x)
chain estimate (~5 re-validations/submit): 268.1 ns saved
```
(Mac dev box: 716.8 -> 530.9 ns, 1.35x.) The absolute host number is
small; the win is removing per-layer redundant work from the serialized
submit path and the principle: per-submission checks stay everywhere,
immutable ones run once.

### dflash2 drafter (same shape, NOT changed — honest negative)

The drafter computes full-vocab BF16 logits for B=8 rows per spec round
(~2.5 ms at TP1 measured geometry) because draft selection needs exact
top-16 per mask row (`SparkQwen38_27bLaunchDsparkSelect`), and the
certified screen provably contains only the top-1 (any candidate with
`upper >= best lower`). A **certified top-K screen is provable** — admit
`upper_c >= Kth-largest lower bound`, same round-up bound arithmetic —
but it means new kernels plus revalidation of the drafter's 96-100%
reference-agreement gate (tools/qwen38_27b_dflash2_vllm_input_parity.py).
Out of near-zero-risk scope for this lane; design ready for a follow-up
lane. The dormant MTP row==1 path DID get the certified route (same
fix as the decode head).
