# cfg-audit lane report — the checked-in-config drift audit (2026-08-29)

Lane: `lane/cfg-audit` (worktree off main `8780fc1`). Mission: the one-shot
audit the k3-finish lane recommended after the K3 rot — for EVERY family that
commits both a config tree and the generator that emits it, regenerate into a
scratch dir and byte-diff. Classify every difference: **(a)** stale config
(generator is truth), **(b)** generator drift (config is truth — fix the
generator), **(c)** ambiguity for the coordinator.

Zero behavioral changes landed: no committed deployment JSON changed content
anywhere in this lane; every fix makes a generator reproduce the already-
committed truth (or a schema validate again). The glm5_next stage configs —
the glm5-dsa lane's surface — were audited **read-only** and are untouched
(`git status deployment/` is empty; the byte-identity receipt is below).

## The two live finds

### 1. glm5_next / glm52 generators produce configs the adapters REJECT — class (b)

Commit 7ceb7cc (r3-flashdecode, 2026-08-29) added
`decode_split_context_threshold` to the serving adapters' EXACT-member lists
(`SparkJsonValidateObjectMembersExact` — a config missing the member is
`SCHEMA_ERROR` at load) and to the 16 committed glm5_next stage configs, but
not to the two deployment generators. Regenerating a deployment with the
then-current tools produced configs the residentd refuses to boot, and the
glm5_next generator's comment still claimed "only these nine". Nothing
committed changed behavior (threshold 0 = split path disabled = shipped
byte-for-byte behavior; the r3 report says the same). Fixed in both
generators (threshold 0, comment corrected); verified post-fix that
`tools/glm5_next_gen_deployment.py --output <scratch>` reproduces
`deployment/glm5_next_tp16` byte-for-byte with the checked-in configs
untouched.

### 2. Ten checked-in deployment specs were un-generatable for two weeks — class (a)

53bda3f (dsv4-pro, Aug 15) made `topology.transport_hosts` a required spec
member. Ten of the thirteen `examples/deployments/*.spec.json` were never
updated: `tools/generate_model_resident_deployment.py` rejected them with
`topology members differ: missing=['transport_hosts']`. Any flow consuming
them (the b1 release shapes, the qwen38 fp8 specs) has been broken since.
Repaired by inserting the member with the generator's own fallback value
(`transport_hosts = rank_hosts`), which reproduces exactly the pre-53bda3f
output; diffs are pure insertions.

### 3. Reported, not fixed — class (c)/(b) adjacent

- `qwen38_tp4_build.sh` line 50 references
  `examples/deployments/qwen38_27b_tp4_host_rdma.spec.json`, which does not
  exist and NEVER existed in git history (`git log --all` on the path is
  empty). The build script's generator step cannot have ever run as written.
  Authoring a new deployment spec is deployment policy, so this lane touched
  nothing — coordinator to route to a qwen38 owner.
- `tests/test_k3_deployment_config.py` — the very gate the K3 rot fix landed
  — was never registered in the Makefile's `PYTHON_TESTS`, so `make test`
  never ran it. Now registered (below).

## The permanent gate

`tests/test_deployment_config_drift.py` (stdlib only, ~3 s, TERM-only,
registered in `PYTHON_TESTS`): regenerates every committed generator→config
pair into a temp dir and byte-compares —

- K3: `k3_gen_deployment.sh` + `k3_gen_adapter_configs.sh` (17 files);
- glm5_next: all 17 files of `deployment/glm5_next_tp16`;
- glm52: emitted stage config must equal the adapter's exact-member list
  parsed from the C source (the check that catches find #1 mechanically even
  with no committed tree);
- generic family: all 13 specs must generate, and the two committed twins
  must byte-match.

Verified both ways: PASS on the fixed tree; FAILS loudly (with the
(a)-vs-(b) classification reminder in the message) with the generator fix
reverted — i.e. it would have caught the r3-flashdecode drift the day it
landed. Recommendation: keep it permanent; it is the mechanical form of this
entire audit.
