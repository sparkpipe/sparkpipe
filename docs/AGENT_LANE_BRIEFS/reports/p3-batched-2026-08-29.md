## Headline

**The premise was a misread; the measured verdict is negative as a route
change, and the lane delivers the proof infrastructure instead.**

1. Kimi's PERF_PROGRAM claim "B1==B2==8.31 because each row re-reads
   29.9GB" does not describe merged main. In the knee-sweep's own CSV,
   8.31 is the **B=1** aggregate; B=2 measured **16.63 aggregate = 2.00x**
   (and B=4 = 33.23 = 4.00x). Small-B decode was already scaling ~2x/4x.
2. Kernel-level bench on spark5 (shipped kernels, 27B FP8 89 MB verify
   shape K=5120→N=17408, 335 matrices = 29.9 GB arena, one "step" streams
   the working set once): the per-row scalar route's concurrent row
   streams **overlap in GB10's memory system** — B=2 costs ~0 ms over B=1
   (232 vs 228 GB/s effective). Scalar aggregate: **2.03x @ B2, 3.36x @
   B4**, equal to the batched kernel at B8 (3.86x vs 3.84x).
3. The new one-weight-stream batched kernel (`SparkLmBatchedLinearKernel`)
   is **bit-exact** against the scalar path per row (host oracle 68
   checks + device spot check: 69,632 neurons, zero mismatches at B=4)
   but pays the shared-staging round trip: **1.53x @ B2, 2.58x @ B4** —
   behind scalar through B4. This is the same scalar-beats-tile gap the
   tile path measured at M=9 (228 vs ~171 GB/s).
4. Per the measurement, the shared gate **keeps the scalar route for
   rows < 16**. The batched kernel stays compiled, oracle-proven, and
   documented at the gate as the one-pass alternative for an
   overlap-hostile bandwidth profile; switching the route is one launch.

## K1 — the dispatch diagnosis (completed, with a correction)

The shared gate `SparkLmHostLaunchBatchedLinear`
(model-families/common/include/sparkpipe/spark_lm_kernels.cuh) routes
`row_count < SPARK_LM_TILE (16)` to the scalar GEMV `SparkLmLinearKernel`
whose grid is `(row_count, N/8)` — grid.x IS the row, so the weight strip
is streamed once per row. Family paths into the gate:

- **qwen38_27B**: FP8 E8M0B128 rows 1..4 routed here explicitly (the
  "rows 1..4 scalar" comment); all non-native formats fall here too.
  Rows ≥ 5 go to the WS GEMM / native MMA (weight-once already).
- **qwen38_max / qwen4_flash**: BF16 dense rows ≥ 2 go to the Mloop
  (weight-once); everything else lands here.
- **dsv4**: rows == 1 only (rows 2..4 have no native bucket); the pair
  and strided launchers run the 1-row kernel per row deliberately
  (bit-identical-to-B1 contract, documented in-file).
- **head shadow** (screened argmax, MXFP4, rows 2..15, 1024-thread CTAs):
  scalar per-row.
- glm52 / K3 / glm53 have separate kernel trees and do not consume this
  header; nothing to inherit there.

## K2 — the fix (built, proven, not routed)

`SparkLmBatchedLinearKernel`: one CTA per neuron strip; every row's
K-chunk (512 floats, ≤ 15×512×4 = 30 KB shared) is staged in shared
memory; each weight word is loaded ONCE and applied to all rows. Per-row
FMA chains mirror `SparkLmDotLinearRow` exactly — same lane-strided run
order (chunk is a whole number of every format's run granularity × warp
width), same decode, same value×scale product feeding fmaf, same tail
handling, same warp reduce — so per-row results are **bit-identical to
the B1 kernel by construction**, on all five weight formats
(BF16/FP8-E8M0-group/FP8-F32B128/FP8-E8M0B128/MXFP4).

## K3 — host oracle (68 checks, all green)

`tests/test_p3_batched_small_rows_host.py` +
`tests/host_cuda/spark_lm_batched_host.cu`: diffs the batched kernel
against `SparkLmLinearKernel` on the same weights at B = 1,2,3,4,5,8,15
across nine format/shape cases (odd-K tail, multi-chunk K=1152, partial
CTAs, 27B-wide 5120×2048, head 32-warp geometry) plus five B=1 pins, and
asserts the dispatch source contract.

To make the whole shared family kernel header host-compilable (the
oracle IS the proof), the lane added the `SPARK_LM_LAUNCH` guard macro:
every launch statement is wrapped; nvcc (which defines `__CUDACC__`)
compiles it, plain C++ elides it. New host shims: `cuda_bf16.h`, `mma.h`
(parse-only wmma stub), `__half2`/`__ldg`/`__ldcs` in the existing fp16
and lm_host_cuda shims.

**Defect found en route (pre-existing, unfixed, now documented in the
oracle)**: the scalar kernel's paired bf16 input loads misalign when K is
odd and row ≥ 1 (row r starts at element r·K = odd pair index). The
multi-row scalar route silently misreads odd-K rows ≥ 1. Rows 2..15 with
odd K are exactly the region the batched kernel would own if routed; the
element-indexed batched kernel is correct there (oracle proves it against
the alignment-valid per-row invocation).
