## R2c — dsv4 bulk causal-prefill kernel: IMPLEMENTED, GPU cell QUEUED

The module header prescribed the replacement ("a causal bulk-prefill
kernel can replace the wavefront after separate qualification");
PERF_PROGRAM2 R2c names the rock. The old `SparkDsv4ModuleRunCausalAttention`
ran one CacheScatter+SparseAttn pair per round-major wave — a
one-sequence chunk executed `rows` sequential near-empty grids.

### Design (exact-equivalence, not approximation)

Causality in the wavefront comes from ring write order: a window read
never observes a slot written by a later in-frame wave. The bulk path
reproduces that read set exactly, in three launches per prefill frame:

1. `SparkDsv4WindowShadowKernel` — per-row snapshot of the lane's
   window ring page BEFORE any scatter (the "pre-frame ring").
2. One whole-frame `CacheScatter` (existing kernel, one launch).
3. `SparkDsv4LaunchBulkPrefillAttn` — the same `SparkDsv4SparseAttnKernel`
   parameterized with (staged_kv, shadow, row_positions): a window slot
   written by an in-frame row (position <= the query's, newest wins)
   reads the frame's staged KV row — the exact bytes the wavefront
   would have scattered before the query read it; every other window
   slot reads the pre-frame snapshot — the exact value wave-serial
   read-order protection provided. Top-k compressed columns, column
   order (oldest->newest), split-K, sink, and merge are untouched, so
   per-row FP op order is identical to the wavefront. `rows == 1`
   keeps the decode path byte-for-byte (`RunAttentionRows`).

The kernel's window-source table is filled serially by thread 0 in
ascending frame-row order (the same per-lane position-order invariant
the wavefront itself relies on for causal correctness), so a slot
shared by two in-frame positions keeps the newest — no new assumption.
