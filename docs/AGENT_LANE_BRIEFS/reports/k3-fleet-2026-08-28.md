## 1. Why the 4-rank slice needs the full 16-rank topology (exact demands)

What the deployment generator (`tools/k3_gen_deployment.sh` +
`tools/k3_gen_adapter_configs.sh`, both on lane/k3-fleet = merged main)
demands, each verified in code on cb3797a:

1. **16 nodes in model_resident.json.** The K3 descriptor declares
   `.stage_count = 16u` with the comment "One node per RANK (the
   hybrid's contract): the residentd checks the node count against this"
   (modules/k3_resident_decode_stage/source/spark_k3_serving_adapter.c:476-495).
   `SparkModelResidentDeploymentValidateForAdapter`
   (runtime/model_resident_deployment.c:451) rejects
   `deployment->node_count != descriptor->stage_count` with
   TARGET_MISMATCH at residentd phase `deployment_validation`. A 4-node
   deployment JSON cannot load, full stop.
2. **rank_index == stage_index == linear rank 0..15** (hybrid geometry,
   runtime/pipeline_runtime.c:120-135: `hybrid && rank_index !=
   stage_index` -> INVALID_ARGUMENT). PP stage = rank/4, TP rank = rank%4.
   The generator's `stage_index = i` is exactly this.
3. **Pipeline neighbors cross the TP group**: rank r's hidden-transport
   previous rank is r-4 and must exist in the node list
   (node/model_residentd.c:1196-1211, SCHEMA_ERROR otherwise). Rank 12
   RECEIVES its decode input from rank 8 (spark8). LIVE RECEIPT from the
   earlier rank-12 run on sparkc (/tmp/k3-residentd-rank12.log):
   ```
   hidden_spark_rdma_fabric_ready device=rocep1s0f1 port=1 rate_gbps=100
   hidden_spark_rdma_open_timeout route=rank8_to_rank12_hidden role=receiver port=62712 waited_ms=120000
   model_residentd initialize=busy status=15 phase=transport_open rank=12 stage=12
   ```
   (That run used the full 16-node model_resident.json — the status line
   says stage=12 — with only rank 12 up: it wired fabric + routes and
   waited at transport_open for a fleet that was not there. The 1-node
   model_resident_rank12.json on sparkc is a superseded experiment and
   also carries stale kv 4096/4096 runtime_limits; the staged 16-node
   config is the correct one.)
4. **Runner-side agreement** (two more locks):
   `spark_k3_resident_decode_stage_runner.cu:710-715` — the
   `stage_count == 4` path binds the PP4 stage tables (layers 0-23 for
   stage_index 0), so a 4-node "slice" deployment would demand the
   STAGE-0 pack, and the PP1/derive path (`world_size/tp_degree == 1`)
   sets `owns_embedding = 1`, which a stage-3 pack cannot satisfy (the
   embed tensor lives in stage-0 packs; stage 3 = layers 70-92 + final
   norm/head tail). Decode needs all 93 layers end to end.
5. **kv page capacities must be 0/0**: the descriptor carries no JIT_KV,
   and `SparkModelServingAdapterValidateRuntimeLimits`
   (runtime/model_serving_adapter.c:174-177) REJECTS nonzero
   kv_logical/physical_page_capacity when jit_kv==0. The generator on
   main already emits 0/0 (commit 3fb101c); any hand-written config with
   4096/4096 dies at phase runtime_limits.
6. **One wave, 180s connect window** (glm53 all-16 lessons): all 16
   residentds near-simultaneously; late joiners refused.

So the exact fleet prerequisite set is: 16 nodes staged
(bin/lib/config/pack each), one residentd per node launched in ONE wave,
packs `k3.stage{s}.rank0{t}.pack` for s=0..3, t=0..3
(spark{hex(4s+t)}), exclusive fleet-wide memory window (section 3).

## 3. Memory math vs the 110 GiB ceiling (checked before lighting)

Per rank node (stage-3 numbers; pool formulas from
spark_k3_resident_decode_stage_cuda.cu:177-260):

- weights: pack 98,119,908,864 B = **91.4 GiB** (mmap + registered)
- KDA state pool: 17 KDA layers x 16 seq x 96*128*128*4 B = **1.59 GiB**
- KDA conv windows (q,k,v): 3 x 17 x 16 x 12,288*4*2 B = **77 MB**
- MLA KV pool (kv_pages=2, page = 64 slots x 1152 B): **< 1 MB**
- scratch (rows=16, routes=16x16): ~3 MB; page tables negligible
- NCCL/transport buffers + CUDA context overhead: order 2-4 GiB

**Total ≈ 95-97 GiB — fits under the 110 GiB ceiling alone with ~13 GiB
margin, empirically confirmed: the ASAN run below loaded and destroyed
the full pack + pools on sparkc with 111 GiB available and exited
cleanly.** It does NOT fit alongside another model's rank: glm5_next's
TP16 fleet holds 21.7 GiB/rank on ALL 16 nodes right now (active debug
lane; reservations in runs/ under holder lane-glm53) — 91.4 + 21.7 >
110 and brushes the ~114 GiB NVRM kill line. **The K3 window is
EXCLUSIVE fleet-wide**: the glm5_next fleet must pause (fleet_swap
semantics) for the window and be restored after. No KV reduction is
needed or used — the deployment's kv capacities are 0/0 by contract and
the module's own pools are the ~1.7 GiB above; the adapter.json
`kv_pages` field is the only KV knob and is currently 2 (smoke-scale;
raise it for real context lengths at bring-up — it stays cheap, ~37 MB
per page per MLA layer set).

## 4. Why no partial wave was launched (rule compliance)

The fleet-only rule exists for exactly this case: ranks without their
fleet sit in transport-wait holding their full weight in unified
memory. A 4-rank stage-3 wave would (a) never reach ready (rank 12
waits for rank 8's hidden route — section 1.3), (b) hold 4 x 91.4 GiB
indefinitely, (c) violate the 110 GiB ceiling with glm5_next
co-resident, and (d) risk the silent NVRM kill for BOTH lanes. TERM
protocol was not needed — no K3 daemon was ever started this session.
