## How this serves the scoreboard

Every serving rank re-reads and re-uploads its whole pack at every process
start (fopen + sequential per-tensor fread+upload, single-threaded) — that is
the cold-start line item on all 16 nodes and every model family, and it is the
cold path the W2 weightd inherits verbatim. This lane makes the load path
overlap read and upload, and makes whole-pack digesting ~8x faster with a
bit-identical value (identity keys depend on that value). Zero arithmetic
changed: the fills are per-tensor independent and the upload order is
preserved by construction (single stream, in-order issue) — the GPU gate
re-runs the retained validator on the lane branch (queued, see runbook).

## What changed (2 commits on lane/w1-loader)

1. `e3c1efc` — L1 + read-pipelined sha256:
   - `runtime/stage_module_common.c`: new `SparkStageModuleLoadPipeline*` —
     one worker thread preads chunks into a 2-slot ring of pinned host
     staging (2×64 MiB, `SPARK_STAGE_MODULE_STAGING_CHUNK_BYTES`) while the
     main thread issues `cudaMemcpyAsync` H2D onto one internal stream,
     strictly in enqueue order, one `cudaEvent` per slot guarding buffer
     reuse. `SparkStageModuleLoadDeviceRegion` keeps its exact signature and
     semantics: env-off (`SPARK_STAGE_MODULE_LOAD_PIPELINE=0`) and small
     regions (<64 MiB) take the retained synchronous body verbatim.
     Fail-closed: a worker read error or copy error poisons the pipeline,
     `Finish` reports it, `Region` after it refuses.
   - `modules/dsv4_resident_decode_stage/source/spark_dsv4_resident_decode_stage_module.c`
     (the reference family per the brief): `SparkDsv4ModuleLoadPack` creates
     ONE pack-wide pipeline and the per-entry payload+scale regions enqueue
     through it — read of tensor N+1 overlaps upload of tensor N across the
     whole directory. `SPARK_STAGE_MODULE_LOAD_PIPELINE=0` restores the
     exact old path.
   - `src/spark_sha256.c`: `SparkSha256File` now overlaps its read pass
     (reader thread, 2×4 MiB, chunks hashed strictly in file order).
     `SPARK_SHA256_FILE_PIPELINE=0` is the sequential reference.
   - `tests/test_dsv4_w1_loader.c`, `tools/dsv4_loader_bench.c` (lane test +
     bench). Code-size ratchet 219673 → 220773 with in-commit justification.
2. `15034b1` — L2 the real fix: aarch64 FEAT_SHA2 bulk transform.
   The read-overlap alone could not win on NVMe: the portable single-block
   transform (~0.25 GB/s measured, below) is the whole tax. Added the ARMv8
   SHA-2 crypto-extension compression (`vsha256hq/h2` + `vsha256su0/su1`
   schedule) as the BULK block path of `SparkSha256Update`, selected at
   runtime (`getauxval(AT_HWCAP)&HWCAP_SHA2` on Linux,
   `hw.optional.arm.FEAT_SHA256` on the Mac), portable loop as fallback,
   `!__CUDACC__`-guarded so nvcc host passes keep the portable path.
   This is the same FIPS 180-4 function — the digest value is unchanged by
   construction, and proven by test (below). h2 operand note for the record:
   `vsha256h2q_u32` takes the PRE-hq abcd; the updated-abcd ordering hashes
   wrong and is caught by the long-message test.

```

5c32c2b28999325bc5ad39d6530bcb46fbdf1f86375a991b7269764c50b0d109  /tmp/w1_sha_bench.bin   <- shasum -a 256
```

That is 26.2s → 3.3s for 6 GiB = **7.9x**, digest bit-identical to the
pre-lane binary AND to `shasum -a 256`. Per-100 GB: ~437s → ~55s. The first
read-overlap attempt WITHOUT the transform measured 26.2s vs 26.1s (no win):
hashing, not reading, is the tax — which is why the transform is in.

Test matrix (`tests/test_dsv4_w1_loader.c`, cuda-stub, all green):

  stream, 1,000,003 bytes, computed with python hashlib, asserted via two

  through every block-boundary path). This is what caught the wrong h2
