## What landed

### Unit 1 — the interleaving contract

New `include/sparkpipe/spark_continuous_batch.h` +
`scheduler/continuous_batch.c`: a step-boundary admission controller over
lane/row arithmetic. A deployment is two budgets — `max_input_rows` (the
R2a budget) and `max_active_lanes` — and the controller enforces the C1
law at every boundary: a join is granted only when the post-join
WORST-CASE round (every resident lane decoding one row while the joined
lane runs its whole prompt) still fits `max_input_rows`, and a lane slot
exists. The refusal is NAMED before anything is touched, in the pager's
discipline (`QUEUE_ROWS` / `QUEUE_LANES` / `QUEUE_OVERSIZE` /
`QUEUE_FULL` / `QUEUE_AHEAD` — arrival never cuts ahead of queued work),
and the offer QUEUES: backpressure is a queue, never a wedge, never a
silent drop.

The three laws, each with a deterministic host proof in
`tests/test_continuous_batch.c` (registered as `test_continuous_batch`,
built like `test_topology_switch` — two translation units, no engine):

1. **L1 bit-exact residents under a mid-flight join.** One run with r101
   (rows 2, 3 tokens) + r102 (rows 4, 3 tokens); a second identical run
   where r103 (rows 3) joins between steps 2 and 3. The residents'
   emission streams — (token_index, step) pairs, slot order — are the
   SAME BYTES in both runs (`memcmp` receipt), they finish on the same
   round, and the row budget law (`rows_spent <= max_input_rows`) is
   asserted after every single state change in every scenario (the
   slice-test discipline).
2. **L2 refusals queue-not-wedge.** Two lanes full, a third offer
   refused `QUEUE_LANES` at every boundary while residents run, admitted
   at exactly the boundary after they finish; counters name every
   refusal; the controller ends empty (`admission_accepted == 3`,
   `slot_reclaims == 3`). Oversize offers (rows > `max_input_rows`)
   never compete (no head-of-line blocking) and are withdrawn by the
   caller; a full queue answers `QUEUE_FULL` and is NOT kept (the pager
   BUSY analog).
3. **L3 slot reclaim at the very next boundary.** A lane finishing at
   step s (emission path) or retired engine-side (the `Retire` seam path)
   frees its slot at the very next boundary, and the boundary's released
   offer takes the freed slot (lowest-free), residents untouched.

The step model exists for the proofs and for `rows_spent` visibility; the
tool seam does not use it (the engine does the rounds there — the tool
only offers / retires / releases).

### Unit 2 — the scheduler policy

`SparkContinuousBatchPolicyPick` is a pure function (plain arrays,
separately provable): smallest `prompt_row_count` first, ties in arrival
order; the starvation escape promotes the OLDEST aged offer (waited >=
`starvation_bound` boundaries) to the boundary's priority pick. The
reservation leg is the sharp part, and it is proven exactly: an aged
offer's refusal closes the boundary to YOUNGER offers even when they fit
— five 1-row residents (rows budget 8) hold S (4 rows) queued; t1 (1 row,
would fit) queues behind S; at S's first aged boundary S refuses
(5+4 > 8) and t1 is still queued after the boundary — the reservation
held. When the residents finish, S admits FIRST (aging flag set on its
lane, `starvation_jumps` counted), t1 follows. The bound, stated honestly
in the header: an aged offer admits at the FIRST boundary whose resident
state alone can hold it, and younger competitors cannot push that
boundary out; no scheduler can admit into a resident set genuinely full
for N rounds (that is L2's queue, not starvation) — what the policy
guarantees is that queued work is not starved by queued competitors.

### Unit 3 — the compile-visible seam (node/model_batch.c ONLY)

`SPARK_MODEL_BATCH_CONTINUOUS` (env, mirroring the file's established
`SPARK_MODEL_BATCH_SEQUENTIAL` pattern) enables continuous mode:
- the controller initializes from the DEPLOYMENT's own limits
  (`runtime_limits.max_input_row_count`, `max_active_sequence_count`) —
  the R2a budget is the seam, as briefed;
- every file request is OFFERED; ADMITTED offers submit immediately
  (idle joins), refused ones wait; an OVERSIZE offer is submitted direct
  (the engine chunk-prefills it) and withdrawn — nothing wedges, nothing
  is lost;
- the run loop releases queued offers at boundaries — after each
  Progress pump — in the controller's policy order; the event callback
  Retires lanes on the engine's terminal events (COMPLETED / CANCELLED /
  ERROR); engine admission closes on the last submit (the drain-to-exit
  contract unchanged: loop runs until `terminal_count == request_count`,
  final view must show zero live/inflight).
`node/model_api.c` untouched (the tokenizer-sidecar lane's write set).
No other runtime file touched — `runtime/model_batch_engine.c` is NOT in
this lane's diff; the engine remains the enforcer of its own admission.

Default OFF: without the env the tool is the BATCH tool it was — the
pipeline-client suite passes byte-identically. WITH the env enabled the
full `test_model_pipeline_client` suite also passes (exit 0, including
the batch-engine scenarios against the fixture residentd ranks) — the
seam is exercised end-to-end on the host, not merely compiled.

## Design notes / honest scope

- The boundary arithmetic is conservative-by-one-round (a join reserves
  its whole prompt against the round that also decodes every resident
  lane). That is the C1 discipline (exact per-lane demand, no exception
  path) and it is what makes L1 hold by construction; the engine's
  chunked prefill can only spend LESS than the reservation.
- The controller is the boundary POLICY layer; the engine's own
  admission (KV pages, request capacity, duplicate ids) remains the
  enforcer. A release whose engine Submit fails propagates the failure —
  same contract as BATCH mode's SubmitAll.
- Deployment law mirrored from `runtime/model_resident_deployment.c`:
  `max_active_lanes <= max_input_rows` is validated at Initialize
  (`INVALID_ARGUMENT` otherwise), pinned in the validation proofs.
- Oversize handling is the one place the seam deviates from pure
  controller rule (submit direct + withdraw): a batch file is a closed
  set the tool must drain, so "never admitted" cannot be allowed to mean
  "never exits".
