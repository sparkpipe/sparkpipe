## The mechanism (D2/D3)

The lean source diff ef8fa302..main (module.c +1008, spark_lm_kernels.cuh
+737, cuda.cu +104) preserves every B1 kernel launch shape (verified hunk
by hunk: rows==1 paths byte-equivalent; HcMix/W13/W2/pro changes are
PRO_BUILD-guarded or rows>1-only). What changed is HOST orchestration:

1. `modules/dsv4_resident_decode_stage/source/spark_dsv4_resident_decode_stage_module.c:880`
   (main): `state->dspark_enabled = 1u;` — hardcoded, no config input.
2. ContinueLayers tap block (~:3814): gated only on compile-time
   `SPARK_DSV4_MODEL_MTP_LAYER_COUNT != 0` (always 3), layer in [40,43),
   and `(rows == 1u || dspark_verify)` — **rows==1 is every B1 no-spec
   decode frame**. Each hit: `SparkDsv4LaunchDsparkTapMean` + **full
   `cudaStreamSynchronize`** — 3 pipeline-draining syncs per token.
3. StageFrameRows (~:2530): `fprintf(stderr,"dspark_staging ...")` before
   any gate — unbuffered stderr write per submission (prefill AND decode).
4. ContinueHeadMax (~:3574): dspark acceptance path + stream sync, gated
   on `dspark_enabled` — i.e. always at main.

Budget check: 40.4 -> 33.5 tok/s is 24.7 -> 29.7 ms/token = +5.0 ms/token.
3 tap syncs + acceptance sync + per-frame fprintf at ~30ms tokens is the
right order of magnitude. Confirmed empirically by A/B in D4 (below).
