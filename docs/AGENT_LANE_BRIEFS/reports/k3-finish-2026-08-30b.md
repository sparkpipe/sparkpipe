## 4. kv_pages: smoke 2 → 64 (the adapter knob was choking every real prompt)

A K3 KV page is 64 slots x 1152 B (MLA latent row: kv_lora_rank 512 +
unrotated 64, BF16) = 73,728 B; the smoke `kv_pages: 2` = **128
positions/sequence** — shorter than all 92 quality fixtures (max 769

5 MLA layers) to 0.62 GiB (stage-3, 7 MLA layers); the 16 checked-in

fixtures need kv_pages=3500 ≈ 25 GiB/rank at 16 sequences — documented

## 5. Wave launcher hardened (shared tool, tested against the live fleet)

`tools/k3_fleet_wave.sh` used `pgrep -x sparkpipe_model` for the
exclusive-window census AND the launch pid capture. The daemon's comm is
identical for every family's residentd — the capture could grab a
FOREIGN daemon's pid into our residentd.pid and a later stop would TERM
it (deployment-blind control). `pgrep -f` alone is not the fix: the
pattern self-matches the ssh wrapper's own bash -c cmdline, which
false-positives DAEMON RUNNING on every node forever (observed live in
this session's first census). Now: enumerate
`pgrep -f 'bin/sparkpipe_model_residentd'`, skip `$$`, cwd-filter the
capture to the rank's runtime root, retry 10 s (setsid -f's child is
only pgrep-visible after exec). Negative test on daemon-free sparke
(no output) and positive on live spark0 both behave; the check run
against the live glm5attractor fleet flags all 16 with zero wrapper
noise. Ratchet 222168 → 222230 exact in two justified bumps
(+37 inherited from the un-bumped d2b35f4 deploy driver, +18 the census
rework, +7 the kv_pages knob documentation); `make offline-gates` green
after each commit.
