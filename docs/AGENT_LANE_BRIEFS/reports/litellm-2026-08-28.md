## L2 — the prompt_token_ids nuance (the lane's central finding)

Upstream contract, from `node/model_api.c` (api_connection /
handle_completion):

- `POST /v1/completions` (and `/v1/chat/completions` path) requires
  `prompt_token_ids` (int array, each <= 260000); `max_tokens` optional
  (default 32, cap 8192); response
  `{"object":"text_completion","tokens":[int,...],"status":0}`.
- `GET /health` -> `{"status":"ok","served":N}`. Everything else 404.
- **There is NO text-prompt path.** No `/v1/models`. Token IDs in, token
  IDs out. (Verified in source; no text branch exists in
  handle_completion.)

Consequence matrix, all empirically verified against
`tools/litellm_mock_upstream.py` (a mock that reproduces the contract
exactly — its own contract sanity):

```
$ curl -s http://127.0.0.1:9101/health
{"status": "ok", "served": 0}
$ curl -s -X POST http://127.0.0.1:9101/v1/completions -d '{}'
{"error": "prompt_token_ids required"}
$ curl -s -X POST http://127.0.0.1:9101/v1/models
{"error": "not found"}
```

1. Transformed route `/v1/completions` (mock behind proxy):
```
$ curl -s -X POST http://127.0.0.1:4100/v1/completions -H "Authorization: Bearer $K" \
    -d '{"model":"mock-openai","prompt_token_ids":[151644,872,198],"max_tokens":3}'
{"error":{"message":"'prompt'","type":"None","param":"None","code":"500"}}
```
The transformed path demands OpenAI `prompt`; it cannot carry
prompt_token_ids. NOT the bridge.

2. Pass-through route `/vllm/v1/completions` — THE BRIDGE, byte-for-byte
proof (mock log records exactly what LiteLLM forwarded):
```
$ curl -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:4100/vllm/v1/completions \
    -H "Authorization: Bearer $K" -d '{"model":"mock-vllm","prompt_token_ids":[151644,872,198],"max_tokens":3}'
{"object": "text_completion", "tokens": [149893, 6106, 1389], "status": 0}
HTTP 200

$ tail -1 /tmp/mock-upstream.jsonl
{"ts": 1787935588.52, "method": "POST", "path": "/v1/completions",
```

prompt_token_ids forwarded VERBATIM; only `model` rewritten to the

3. Deployment model strings must use the `vllm/` prefix (the only provider
with a registered passthrough config in 1.74.0):
```

```

4. Error fidelity: upstream 400/500 surfaces to the client as HTTP 500
(generic body), but the upstream status text is preserved server-side:
```
proxy log: litellm.llms.vllm.common_utils.VLLMError: {"error": "prompt_token_ids required"}
down case:  litellm.llms.vllm.common_utils.VLLMError: Cannot connect to host 127.0.0.1:9999 ssl:default [Connect call failed ('127.0.0.1', 9999)]
```

5. LiteLLM's own `GET /health` per-deployment probe speaks the OpenAI chat
shape — our upstream always rejects it, so it reports our deployments
"unhealthy" even when healthy. Documented; do not use it as the fleet
liveness truth.

## Honest limitations / next steps

1. **Live completion through the proxy is owed** the moment any upstream
   comes back: `curl :4000/vllm/v1/completions -d '{"model":"glm-5.3-flash",
   "prompt_token_ids":[...],"max_tokens":8}'`. Everything is staged for it.
2. spark9's 27B port is provisional (8434); confirm at launch and update the
   config's routing table + this report.
3. Error fidelity to the CLIENT is degraded (everything non-2xx -> HTTP
   500, generic body; upstream text only in the server log). If client-
   visible fidelity matters, that is an upstream/model_api concern or a
   thin adapter — not fixable in LiteLLM config.
4. No DB: single master key; per-key budgets/virtual keys/spend dashboards
   need `database_url` (documented in the runbook).
5. The upstream speaks token IDs end to end; tokenization is the client's
   job today. A text facade belongs in model_api or a sidecar, not here.
