# Build notes

Explanations that used to live as comments in the build files. Each note names the variable or rule it explains.

## Makefile

- **`spark-cc-supports`**: Architecture tuning for auto-vectorization. The tokenizer and other hot loops are written as portable scalar C that the compiler auto-vectorizes; these flags tell it which vector units the build host actually has, so it emits AVX2 on x86 and NEON or SVE2 on an Arm Grace host, from one source with no intrinsics. ARCH_TUNE_FLAGS can be overridden or set empty for reproducible or cross builds. On Arm the Grace core is Neoverse V2; older compilers that do not know that name fall back to -mcpu=native. The flag is probed so an unsupported one is dropped rather than breaking the build.
- **`sp_objects`**: Source path to object path, for any source under any directory. The full source path is preserved under build/obj so two files with the same basename in different directories cannot collide. A prefix-stripping patsubst cannot do this: it returns a non-matching entry unchanged, which is how seven .c paths came to sit in *_OBJECTS and abort the parse via -include.
- **`$(CORE_OBJECTS)`**: Every object is built by the one rule below. Include flags are attached per object list rather than per directory, so moving a source does not change how it is compiled.
- **`build/obj/runtime/spark_weightd.o`**: W2 weightd (docs/WEIGHTD_DESIGN.md): the daemon core and the serving-side attach helper reach <cuda_runtime.h>/<cuda.h> (the VMM surface), so they compile with the model-common include shape - the stub headers where CUDA_HOME is absent, the real ones where it exists.
- **`K3_SERVING_ADAPTER`**: Pro serving topology selection: 404 = TP4xPP4 hybrid (default), 16 = TP16, 4 = TP4, 404-B1 = TP4xPP4 bucket-1 variant. The adapter id and the adapter
- **`TOOL_NAMES`**: Topology/lane specialization for the shared adapter source (TP1 whole-stack
- **`all`**: Model CUDA modules are immutable artifacts selected by an explicit model package. Host builds never guess a codec or silently skip a CUDA artifact.
- **`HOST_CUDA_CXX`**: Host-executed KDA run-contract gate (the CUDA CPU shim needs GNU g++: tests/host_cuda_compiler.py's search, as a make probe).
- **`build/sparkpipe_registrar`**: Fleet startup protocol phase 1+1b registrar (docs/archive/FLEET_STARTUP_PROTOCOL.md): pure POSIX TCP, poll-driven, no threads; deliberately links NOTHING — it must start in milliseconds on every node with zero library dependencies.
- **`$(K3_TP16_SERVING_ADAPTER)`**: The K3 adapter links the CUDA serving TUs (runner, dispatch, driver) with nvcc, so the rule is the single-spark gate's link line plus the shared libs. nvcc/spark-gated: no nvcc on the build host (offline mac gate) leaves the artifact unbuilt instead of failing `make all` — same contract as below; a spark node builds and validates it for real.
- **`build/test_gemm_descriptor_cache`**: Header-only cache plus a mock encode; the driver stub's cuda.h is what lets runtime/tensor_map.h compile with no CUDA toolkit, and its stub.c stands in for cuTensorMapEncodeTiled so the production entry point is exercised too. -x c++ on the stub keeps the symbol mangling identical to the test TU's (the stub predates C and C++ disagreeing on the name).
- **`build/libdsv41_flash_kernels.so`**: Numeric verification of the math-audit fixes: includes the family's kernel source (`model-families/dsv41_flash/source/dsv41_flash_kernels.cuh`), so those kernels are the production code. The hyper-connection kernels it exposes come from `tests/cuda/dsv41_flash_hc_reference.cuh`, a test-only reference that no production stage launches; production runs `inference/kernels/hc.cuh`.
- **`build/test_model_api_text`**: The sidecar lane's API-edge proof: the REAL model_api serving text over HTTP against the host resident stack (test adapter's deterministic token ids), plus the 400-when-no-tokenizer contract.
- **CUDA sm_121a compile gate's toolkit**: `tools/cuda13_sm121a_compile_gate.sh` requires `release_toolkit` (CUDA 13.0, the release build hosts' toolkit) and CI's compile-sm121a job runs the matching `nvidia/cuda` devel image, pinned by digest in `.github/workflows/cuda13-sm121a-compile.yml`. The gate's audits judge compiled code, and ptxas allocates registers differently from one release to the next (CUDA 13.3.1 spilled grouped expert GEMV variants that 13.0 keeps in registers), so the gate checks what ships. `tests/test_cuda_gate_toolkit.py` refuses an image and a `release_toolkit` that differ. A toolkit upgrade is its own change: it moves the release hosts, the image and `release_toolkit` together and reruns the audits and the variant timings. `tools/get_cuda.sh` and `tools/install_cuda13_compile_only_debian13.sh` set up compile-only machines and do not build releases. The gate prints each phase's wall and cpu time (`gate phase: ...`) in the job log.
- **CUDA sm_121a compile gate's failure output (`gate_fail`)**: every phase of `tools/cuda13_sm121a_compile_gate.sh` that captures a command's output in `logs/` reports a failure through `gate_fail`: it prints `tools/build_log_errors.py`'s excerpt of that log, then the phase's message, and exits with the phase's code (12 an exact-target translation unit, 5 the adapters and CUDA programs, 11 the stage-runner binaries, 9 the dependent-wait audit, 8 the nvrm launch arguments, 6 the hosted release root, 10 the spill audit). A parallel build's log is thousands of lines of warnings, each followed by indented source text, and the failing command may sit far from the end, so neither a search for the word "error" nor the log's tail finds what failed: the stage-runner phase used to print the first twenty lines containing "error", which were the source lines of warnings in files that use the error-site macro, and the adapters and exact-target phases printed nothing. The excerpt takes the lines that say what failed, which start in the first column (a compiler, linker or toolkit error, a Python exception, a line a tool marks `REFUSED` or `FAIL`, and make's own lines, which name the targets), prints each once with its line number in the log, its repeat count and the indented source lines under it, and prints the log's last lines when it finds none. The audit phases add their own summary lines with `--also`. `tests/test_build_log_errors.py` checks the excerpt on logs shaped like the gate's, runs `gate_fail` itself, and refuses a phase that captures a log without reporting it.
- **`STAGE_RUNNER_BINARIES`**: Every CUDA binary that links `$(RUNTIME_LIBRARY)` through nvcc: the serving adapters, including the Qwen3.8 27B TP1-TP8 and DeepSeek V4.1 Flash TP4 and rows16 adapters that no `*_SERVING_ADAPTER` variable names, the runner and verify-frames tests, the DeepSeek V4.1 Flash replay and fused-exact test and the K3 TP programs. They depend on the CUDA device library, because the runtime library holds weightd's code, which calls the device layer (`SparkDeviceMemory*`, `SparkDeviceInitialize`) in `libsparkpipe_device_cuda`; a binary that pulls weightd in must also link `$(DEVICE_CUDA_NVCC_LINK)`, and a rule that links the device library without depending on it fails with `cannot find -lsparkpipe_device_cuda` when built on its own. The CUDA sm_121a compile gate, which CI runs, builds and links every one of them (exit 11 when one does not link), and `tests/test_stage_runner_link_rules.py` refuses an nvcc rule that links the runtime library without being in the list, and a rule that links the device library without depending on it. A recipe links the runtime library when it names it or a variable that reaches it, such as `$(ADAPTER_LIBRARIES)`; every target of a rule head is checked on its own, and every list entry must be such a target, so a rule the test stops seeing fails it. The drafter modules join the list through `$(DRAFTER_MODULES)`. An nvrm twin (`$(call NVRM_TWIN,...)`) must be in `NVRM_SERVING_ADAPTERS`: the hosted release gate (`--complete`, in the same CI job) builds and links the twins of `NVRM_SERVING_ADAPTER_SOURCES`, and the two proof twins (Qwen3.8 27B BF16 TP1, DeepSeek V4.1 Flash TP4) are built by `make nvrm-adapters` for the nvrm proofs on a GB10, named in the test's `PROOF_TWINS`. GPU tests are otherwise built only on a GB10, so before this a missing link went unseen: the eight verify-frames tests stopped linking when weightd's memory moved to the device layer (528b2e9a4), which showed only when they were next built on a GB10.
- **`build/sparkpipe_weightd`**: W2 weightd (docs/WEIGHTD_DESIGN.md): the residency daemon and its serving-side attach consumer live in $(RUNTIME_LIBRARY) (the client is the library's import surface); the daemon links like model_residentd - real cudart + libcuda where CUDA_HOME exists, the host stub where it does not - and its tests are stub-pinned like test_stage_module_common.
- **`build/test_weightd_map`**: W3 weightd (docs/WEIGHTD_DESIGN.md): the fd tier - chunk shareable-fd export over SCM_RIGHTS and the consumer's import/map, including a real forked consumer process for the cross-process receipt. Stub-pinned like its W2 siblings.
- **`build/test_driver_compiler`**: The driver compiler and loader: modules published to a library, drivers and model packages compiled (variants, reuse, stale and missing inputs, archives), and a compiled driver loaded through admission and one frame.
- **`OFFLINE_GATES`**: ===================================================== THE OFFLINE GATE SET (red-gate lane, 2026-08-28). The kimi audit found the previous "zero red gates" claim ran a selection of gates, not a set. This variable IS the set: a claim of an "offline gate pass" means exactly `make offline-gates` succeeded, and nothing else. build-all          make -j1 all          (fresh build, the README path) run-tests          make -j1 test         (every registered C test binary that builds on this host + every registered python gate: code-size ratchet, dry-law, staging manifest, the memory-contract ratchet, ...) package-manifest   tools/source_package_gate.sh (manifests of a git archive of HEAD) Hardware-gated work is NOT part of an offline pass and must never be claimed by one: nvcc/CUDA artifacts (the K3 serving adapter, the hardware_* tools) SKIP with a notice when nvcc is absent and are validated on spark nodes. C test binaries that a host cannot build are skipped by `make test` with the same notice contract. =====================================================

## sources.mk

- **`SPARKPIPE_CORE_SOURCES`**: Every host source, by the library it lands in, at the path it actually lives. This replaced four per-directory sources.mk files. They encoded the directory twice - once in the file's own location and once in the paths inside it - and the reorganisation moved twelve sources without updating either. The Makefile then mapped source to object with $(patsubst src/%.c,...), which returns a non-matching entry UNCHANGED rather than failing, so seven .c paths ended up in *_OBJECTS and one of them was fed to -include as a makefile: runtime/filesystem.c:19: *** missing separator.  Stop. One list and one path-preserving object map means a source can move to any directory and only this file changes.
- **`SPARKPIPE_TRANSPORT_SOURCES`**: Transport, memory link, collectives, tokenizer, KV store, stage module ABI. Formerly model-families/common/src, which is the directory the handoff records as deleted twice with every gate green, because it was named for who shared it rather than what it is.
