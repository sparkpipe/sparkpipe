# SparkPipe Fleet Project Handoff

Date: 2026-08-26 UTC

Repository: `https://github.com/sparkpipe/sparkpipe`

Working branch: `codex/hardware-neutral-platform-design`

## Executive summary

This attempt did not produce the intended result. After more than a day, there is
no current, accuracy-qualified exact-32K B1/B8/B64 performance point for any
model, no measured improvement over SOTA, and no production-ready new model
driver. The dashboard's qualified `Solutions` score is therefore zero for every
model.

Some useful infrastructure, contracts, tests, storage evidence, and two narrow
context-capacity fixes were produced. Those are inputs to future work, not a
working inference platform. The multi-agent system consumed substantial effort
while generating almost no integrated model or benchmark progress. Its static
PERT and queue counts must not be treated as evidence that work is executable or
advancing.

The best restart is not to resume the entire fleet. Start with one model and one
four-Spark team, prove one short code-to-hardware-to-measurement loop, and expand
only after that loop repeatedly produces accurate measurements or measured
improvements.

## Intended architecture and non-negotiable requirements

A future implementation should preserve these decisions:

- Hardware-neutral backends: NVIDIA CUDA/Spark, AMD ROCm, and Mac Metal.
- OpenAI-compatible API serving through decentralized compute islands. A model
  instance runs on a local hardware island unless a deliberately supported
  disaggregated mode is selected.
- Batch sizes B1 through B1024 and contexts through 256K where the model and
  memory budget permit. Larger batches may reduce allowed context.
- Weight artifacts at 4, 5, 6, 7, 8, and 16 bits. Limited weight storage must
  not force low-accuracy arithmetic; 16-bit operations accumulated in FP32 are
  acceptable.
- TP, PP, and EP at 2/4/8/16 and useful combinations. TP4xPP4 is the default
  large-model topology; TP16 and PP16 are special cases, not defaults.
- The 100 Gbps switch supports direct any-to-any traffic. Waterfall model
  copying is obsolete.
- KV entries must be sharded to approximately 1/N of the unsharded amount, with
  selectable KV resolution.
- JIT KV prefetch from each Spark's 2–2.5 TB internal-NVMe backing is critical.
- Ceph stores one verified warm model copy. Each Spark receives only the rank or
  stage artifacts needed for its active topologies; node-local NVMe is primarily
  for active artifacts and KV.
- A declarative model recipe resolves to a mnemonic identity and deterministically
  creates or recovers its packs, kernels, topology, precision, and KV decisions.
- Only active model configurations live in VRAM. Warm swaps should take roughly
  10 seconds to one minute. Small models may coexist with a large model when the
  resource plan permits it.
- Providers contribute hardware capacity and pay the platform 10% of sold
  capacity in compute, not cash. API users pay for tokens.
- Performance must be tracked as an accuracy-qualified matrix over context,
  batch, topology, and speculation. A useful scalar may aggregate
  `prefill_rate * decode_rate`; missing or inaccurate measurements contribute
  zero.
- Production efficiency is judged by qualified `Solutions / production_LOC^2`.
  Exploratory probes are valuable only when they answer a concrete question
  with actual data. Exploratory probes do not require an independent audit;
  production changes do.

## Why the agent system failed

1. Orchestration was built before proving one productive end-to-end loop.
2. PERT decomposition was mechanically inflated. Many generated bites restated
   acceptance criteria without naming a real interface, source file, command,
   input artifact, or outcome-dependent next action.
3. Static coverage and ready counts were presented as throughput. They hid the
   fact that the runtime scheduler had no selectable work.
4. Foremen spent turns classifying and rejecting weak results rather than
   dispatching tests, analyzing measurements, or landing small fixes.
5. Provider races generated heavy token traffic and repeated API failures, but
   almost no independently approved, tested, integrated solutions.
6. Queue and lifecycle bugs repeatedly created false-ready, stale-waiting, and
   occupied-but-dead states. Fixes often repaired symptoms rather than the
   source invariant.
7. Spark work was not generated automatically from a model's next unanswered
   question. The hardware stayed idle while agents discussed readiness.
8. The dashboard emphasized agents, calls, queue states, and catalog size more
   than qualified inference results.
9. Tasks were frequently too generic or too large for OxAlpha. Large generated
   patches were rejected as AI slop; line count is a cost, not productivity.
10. Management stayed centralized in the coordinator despite an intended
    self-driving queue, producing serialization and dependence on foreground
    runtime.

## What to trust and what not to trust

Trust:

- A merged commit plus clean deployment provenance plus raw hardware output.
- Exact model/checkpoint hashes, complete manifests, and authoritative pack
  verification.
- Accuracy-qualified prefill and decode rates with batch, context, output
  length, topology, hardware, code revision, and speculation recorded.
- Negative experiments that tested a plausible hypothesis and captured decisive
  raw data.

Do not trust by itself:

- PERT coverage, ready counts, agent turn counts, token volume, patch LOC, API
  call counts, queue health, process liveness, or a dashboard green state.
- A branch-level run as proof of merged-main deployment.
- Plausible text output as numerical correctness.
- File counts without hashes and atomic publication.
- A benchmark without exact context/batch/topology and clean-code provenance.

## Recommended restart

### Phase 1: prove one productive loop

Use DeepSeek V4 Flash on spark4–spark7 because it has the shortest path from
existing parity evidence to a real exact-32K measurement.

1. Use one coordinator, one model launcher, one benchmarker, and one file
   administrator. Do not start the broad PERT/OxAlpha fleet.
2. Correct the DSV4 Flash ceiling to 33,024, test it, audit it, merge it, pull
   clean `main` on all four Sparks, rebuild/install, and restart.
3. Verify exact checkpoint identity, four current packs, configuration, KV
   capacity, and zero source drift.
4. Run exact-32K B1 correctness. Capture raw tokens/logits or the established
   oracle comparison, prefill rate, decode rate, and complete provenance.
5. Run B8 and B64 capacity/rate probes. A failed capacity probe is useful if it
   reports the first limiting allocation or kernel.
6. Profile the largest measured wall and make the smallest plausible change.
7. Retain a production change only after a repeated, accuracy-qualified gain of
   at least 1%. Audit, merge, clean-deploy, and remeasure it.

The first success criterion is not a scheduler metric. It is one row containing
an accurate exact-32K B1 prefill rate and decode rate from clean merged code.

### Phase 2: demonstrate repeatability

Repeat the loop until three successive iterations each produce one of:

- a new qualified matrix cell;
- a measured gain of at least 1%; or
- decisive negative evidence that changes the next experiment.

Only then add Qwen 27B TP4 as a second model lane. Keep storage I/O parallel with
GPU work, but keep model leases exclusive where required.

### Phase 3: revive bounded parallelism

If the first two phases work, revive only executable bites that include:

- exact source files or hardware artifact;
- one expected code or data change;
- an exact command that runs now;
- a pass/fail measurement;
- the next action for success and failure;
- a disjoint write/resource set.

One foreman should own one model and update its next experimental questions from
measurements. OxAlpha should receive only short implementation or analysis bites.
The scheduler should reject a bite at admission time if it lacks an executable
command or required data; it must never count that bite as ready.

### Phase 4: expand the platform

After model hill climbing is demonstrably productive, run non-Spark tracks in
parallel: model recipe/schema, API compatibility, compute-island routing,
metering, provider/user UI, AMD backend, Metal backend, KV tiering, and SOTA
collection. Each track still needs direct code plus tests or a measured artifact;
documents and schemas alone are not completion.
