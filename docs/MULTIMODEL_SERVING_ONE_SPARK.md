# Multi-Model Serving on a Single Spark Box

Status: field guide, assembled 2026-08-25 from live fleet operations
(K3 TP16 provisioning turn). Every command shown is one that ran against
the fleet as written; facts marked **[measured]** were observed directly,
the rest cite `COORDINATION.md` / `tools/devcycle/fleet_registry.json`.

This document covers both meanings of "multi-model on one box":

- **Pattern A — several different models resident on one spark** at once
  (the always-on bands plus the current big model).
- **Pattern B — several ranks of one model on one spark** (TP-in-a-box:
  gates, proofs, small-topology debug), which has its own NCCL rule.

---

## 1. What one box gives you

| Resource | Fact | Constraint it imposes |
| --- | --- | --- |
| Memory | 128 GB unified (119 GB visible) **[coord]** | 2–3 resident models fit; memory is *not* the binding constraint |
| GPU | ONE device (GB10, sm_121a / compute_121a) | all residents share device 0; multi-rank-per-GPU needs an env opt-in (§7) |
| Network | two rails: switched 100 GbE (`enp1s0f0np0`) + direct pair (`enp1s0f1np1`) **[coord]** | RDMA fabric share is an exclusive claim per residentd |
| CUDA | 13.0 at `/usr/local/cuda-13.0` | gencode pairs use `compute_121a,sm_121a` |
| NVMe | `sparkdata/` holds one runtime root per model | roots are large (K3 TP16 ≈ 100 GB pack per rank); check `df -BG` before staging |

A residentd deployment claims, per rank: GPU memory, a TCP control port,
collective listen/peer ports, a transport control port, an RDMA fabric
share, and a KV backing directory. Nothing else conflicts **[coord]**.

## 2. Who may coexist with whom (tier model)

From `COORDINATION.md`; enforcement lives in
`tools/devcycle/fleet_registry.json` + `tools/fleet_swap.sh`:

| Model | Tier | Scope | Hosts | Ports (ctrl / coll / transport) |
| --- | --- | --- | --- | --- |
| Qwen 3.8 27B | always-on | band | spark0-3 | 17480 / 61620 / 58700 |
| DSV4 Flash | always-on | band | spark4-7 | 18480 / 62620 / 59700 |
| GLM 5.2 | big | band | spark8-f | 19480 / 63620 / 60700 |
| DSV4 Pro | big | fleet | spark0-f | 20480 / 64620 / 61700 |
| K3 | big | fleet | spark0-f | 21480 / 61620 / 62700 |

Rules:

1. The two always-on bands run concurrently with each other and with
   exactly **one** *current big model*. That is the standing dev-active
   state of any healthy box in a band.
2. Big band models are mutually exclusive inside their band.
3. Fleet-scope big models evict everything (including always-on).
4. **Never start or stop a big model's residentd by hand** — swap through
   `tools/fleet_swap.sh MODEL` so `/tmp/sparkpipe_fleet_state.json`
   (authoritative copy on spark0) stays true. Hand-starting is reserved
   for non-big deployments and single-rank debug.
5. Dev-active coexistence (residentds up, kernels idle) is always OK.
   *Measured* runs need host-level exclusivity on the measured hosts;
   promotion via swap costs <60 s, so measure in windows (§9).

## 3. Anatomy of a per-box runtime root

Every model keeps a self-contained tree per host under
`/home/<host>/sparkdata/<name>.<format>.<topology>`:

    /home/spark1/sparkdata/k3.mxfp4.tp16/
    ├── bin/sparkpipe_model_residentd      # daemon, one process per rank
    ├── bin/sparkpipe_model_batch          # serving client (optional but recommended)
    ├── lib/libk3_serving_adapter.so       # model adapter (+ .bak-* backups)
    ├── lib/hidden_transport.so            # host transport where used
    ├── lib/runtime_libs/libnccl.so.2      # pinned NCCL the backend dlopens
    ├── config/adapter.json                # PER-RANK config (tp_rank differs!)
    ├── config/model_resident.json         # whole-world deployment description
    ├── packs/k3.tp16.rank01.pack          # this rank's weights (v2 format)
    └── kvcache/                           # KV backing directory

Conventions that keep boxes multi-model-safe:

- Separate runtime root per model per topology — never share or symlink
  across models; a swap touches only its own root.
- Keep every overwritten file as `cp -n file file.bak-$STAMP` first
  (rollout scripts do this); backups make hand-rollbacks trivial.
- Pin NCCL inside the root (`lib/runtime_libs/`) so a system NCCL update
  can not silently change collective behavior under a running model.

## 4. The config pair (what actually differs per model)

**adapter.json — one per rank**, generated by
`tools/k3_gen_adapter_configs.sh OUT_DIR <degree>`. K3 TP16 example
(`spark1.json`, trimmed):

    {
      "stage_pack_path": ".../packs/k3.tp16.rank01.pack",
      "tp_degree": 16, "tp_rank": 1, "world_size": 16,
      "max_sequences": 16, "max_rows": 1024,
      "context_tokens": 4096, "capture_graphs": 1, "hidden": 7168,
      "device_collective": {
        "backend": "nccl",
        "backend_module_path": "lib/runtime_libs/libnccl.so.2",
        "local_host": "spark1",
        "listen_port": 64620,
        "peer_hosts": ["10.20.0.10", "...", "10.20.0.25"]
      }
    }

**model_resident.json — one per world**, generated by
`tools/k3_gen_deployment.sh OUT 16`: schema v2, `coordinator_rank_index`,
adapter/driver shared objects, transport block
(`control_port_base` = the model's transport port base), `runtime_limits`
(notably `max_input_rows`), and one `nodes[]` entry per rank carrying
`runtime_root`, `node_target`, `kv_backing_directory`, and its
`control_endpoint` (host + port from the registry block).

Preflight before any boot verifies exactly the invariants that have bit us:
degree/world/rank coherence, context/rows limits, no stale `kv_pages` pin,
non-empty pack, NCCL present, and `runtime_limits.max_input_rows` patched
on both sides. See `tmp/k3_tp16_rollout.sh push` for the canonical checks.

## 5. Provisioning a new runtime root on a box (idempotent recipe)

Binaries seed host-to-host from a good source root; packs arrive
resumable; nothing is ever partially trusted:

    # bin + lib + configs (skips unreachable hosts loudly, rerun later)
    bash tools/k3_stage_runtime_tp16.sh SOURCE_HOST CONFIG_DIR [ONLY_HOST...]

    # packs: rsync --append-verify + remote sha256 against SHA256SUMS.tp16
    # (run ON the pack node; k3_deploy_tp16.sh is the all-16 version)

Verification = remote `sha256sum` compared to the production checksum
manifest line, never a local pre-copy hash. Every step tolerates re-run:
unreachable hosts skip, partial rsyncs resume byte-exact, configs get
timestamped backups. This exact chain provisioned eight K3 ranks
(≈25 GB binaries+libs, ≈93 GiB pack each) on 2026-08-25 **[measured]**.

## 6. Pattern A — several models resident on one box

1. Check the box is free at the tiers you want:
   `tools/devcycle/fleet_status.sh` (one line per host: rank+cwd or free).
2. Ensure port/KV/RDMA disjointness by staying inside the registry blocks
   (§2). Two models must never share a (host, control-port) pair; KV dirs
   are already disjoint because roots are disjoint.
3. Start each non-big model exactly as its session's rollout script does
   (`setsid nohup bin/sparkpipe_model_residentd --deployment
   config/model_resident.json --rank-index <i> >> log 2>&1`).
4. For the big slot use `tools/fleet_swap.sh MODEL` — it snapshots who was
   running, stops them, starts the new big model, and can restore.
   `tools/fleet_swap.sh status` prints the current designation.
5. Re-probe with `fleet_status.sh` and record the probe WITH any receipt.

Memory budgeting rule of thumb from live footprints **[coord]**: DSV4 Flash
TP4 ≈ 38.5 GB device + 11 GB pack per rank; Qwen 27B PP16 ≈ 2.9 GB pack per
rank. Sum device+pack+KV ceiling per box and keep ≥15% headroom.

## 7. Pattern B — multiple ranks of one model on ONE box

The gate/proof case (worlds {2,4} on a single spark) works, with one
non-negotiable environment flag discovered 2026-08-25 **[measured]**:

    FAIL  ncclCommInitRank result=5 "invalid usage"
    WARN  init.cc: Multiple Ranks are using the same GPU/Partition.
          Set NCCL_MULTI_RANK_GPU_ENABLE=1 to enable this configuration.

NCCL 2.30.7+cuda13.0 refuses N processes on device 0 unless:

    export NCCL_MULTI_RANK_GPU_ENABLE=1     # must be set in EACH rank's env

Notes that cost us an hour:

- The flag must cross **into** the remote shell. `ssh host VAR=1 cmd`
  does NOT propagate env; embed the export in the remote command string
  (see `tools/k3_tp16_tuesday_boot.sh` phase_gate's remote_script).
- With it set, world={2,4} bootstraps `ncclCommInitRank` cleanly and the
  live bf16-sum / u64-max exchange legs pass **[measured]**.
- Each rank still needs a distinct `--rank-index` and its own
  control/collective ports; on one box that means distinct ports per rank
  (the multirank gate derives a free TCP port per run instead of fixed
  bases — copy that trick for ad-hoc worlds).

## 8. Boot, verify, troubleshoot

    tmp/k3_tp16_rollout.sh boot     # ~simultaneous setsid start on all ranks
    sleep 75                        # NCCL bootstrap allowance
    tmp/k3_tp16_rollout.sh status   # pid + :21480 listen + log counters per rank

- Status greps each rank's `residentd-boot-$STAMP.log` for
  `backend=nccl.*tp_degree=16` and error classes
  (`INVALID_ARGUMENT|IO_ERROR|INIT FAIL|SCHEMA_ERROR`).
- Pack-loader failures surface as `VALIDATION_FAILED`; scan with
  `grep -c VALIDATION_FAILED` per rank log. A red rank = regenerate that
  rank's pack (`k3_shard_one.py FULL OUT DEGREE RANK`), redeploy, reboot
  just that rank.
- A rank that never binds its control port within ~900 s is the Phase-4
  abort signal (playbook §5 recovery: fabric link ethtool check/bounce,
  mount checks, fsck-health, boot-unblock drop-ins — all scripted in
  `tools/k3_tp16_tuesday_boot.sh` phases `wait,recover`).

## 9. Serving a request + measuring tok/s

Client (lives in the runtime root's `bin/`):

    bin/sparkpipe_model_batch         --deployment config/model_resident.json         --runtime-root .         --batch batches/o128_batch.json      # B1, 128 output tokens

Batch files are model-agnostic JSON (schema_version 1:
`requests[].prompt_token_ids`, budgets, stop tokens) — see
`tools/devcycle/batches/o128_batch.json`.

Measured decode rate (the receipt format PERFORMANCE_STATUS rows want):

    python3 tools/model_stream_decode_benchmark.py --output receipt.json --       ssh -o BatchMode=yes HOST '<root>/bin/sparkpipe_model_batch ...'
    python3 tools/devcycle/matrix/summarize_run.py receipt.json

Discipline: warmup run discarded, then reps; exclusive hosts during the
window; fleet probe saved with the receipt; hourly-artifact rule applies
(landed commit, qualification receipt, perf row, or green gate).
