Batching is the lever.

Decoding is bound by memory bandwidth: a step takes about as long as reading its weights once, and one read serves every request in the step. So aggregate throughput climbs with the batch. On sixteen Sparks at 1K context the memory-bound ceiling runs from 125 tok/s for one stream to about 2,800 tok/s for 256. SparkPipe is projected to reach 100 for one stream and 2,200 at 256.

memory-bound ceilingprojected, after the planned kernel and collective work

Ceiling: bytes read per step at 273 GB/s per Spark, 1K context, at the deployment precision — FP8 expert weights, BF16 attention, KV cache and activations. Projected: the M1/M2 exit criteria from the roadmap — 80% of the ceiling for the whole step, after the planned kernel and collective work. These are projections, not measurements; the arithmetic is in PERFORMANCE_STATUS.md. At 256 streams each stream sees about 8.6 tok/s.

Determinism

Receipt, not a claim

Same inputs, same tokens, to the bit.

Repeat a request on the same driver build and weights and it returns the same tokens, bit for bit. Every request logs its seed and every output token, which is exactly what an off-node replay needs. That is what lets the provider network verify its providers. Batched runs repeat when the batch does; making them independent of the batch is on the roadmap.

Fabric

Measured 2026-08-13

Two rails. One collective service.

The CRS804 is the all-to-all rail, not a fallback. Pairwise direct links add a second active rail. SparkPipe pins both routes and picks a topology-aware all-reduce from the exact communicator, datatype and payload bytes. For large tensors, two counter-rotating half-payload rings alternate direct and switched edges, so every Spark sends and receives on both ports at once.

Engine

C and CUDA, from scratch

Models compile to drivers.

The kernels, the RDMA transport, the tokenizer, the scheduler and the cache all live in one tree. A model is not interpreted at runtime; it is linked.

Firmware modules

Each model links into one driver from content-addressed, validated modules. At runtime there is no graph interpreter, no kernel search and no fallback.

Every batch size

Kernels are built for every row count from 1 to 1024, so a step's weight read serves the whole batch.

Priorities and deadlines

Each request carries a priority and a deadline. The engine ages priorities so nothing starves, and cancels work that runs past its deadline.

One door

A LiteLLM proxy routes by model name, streams tokens and issues keys. Any OpenAI SDK works unchanged.

Promotion · target

Active models stay resident; others promote from verified NVMe tiers within 60 seconds, from a pooled store read at 20 Gb/s.

Scale in steps

Deploy 4, 8 or 16 Sparks without changing the API or model packages. Adding Mac Studios one at a time is planned.

API

OpenAI-compatible

Any OpenAI client works.

Point your client at SparkPipe's endpoint. Two extras come with it: a seed that replays a sampled reply token for token, and a deadline after which the engine cancels the request.

curl https://sparkpipe.ai/v1/chat/completions \
  -H "Authorization: Bearer $SPARKPIPE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "glm-5.3-flash",
       "messages": [{"role": "user", "content": "Hello"}],
       "temperature": 0.7, "seed": 42,
       "deadline_ms": 30000, "stream": true}'
import os
from openai import OpenAI

client = OpenAI(base_url="https://sparkpipe.ai/v1", api_key=os.environ["SPARKPIPE_API_KEY"])
reply = client.chat.completions.create(
    model="glm-5.3-flash",
    messages=[{"role": "user", "content": "Hello"}],
    temperature=0.7,
    seed=42,
    extra_body={"deadline_ms": 30000},
)
print(reply.choices[0].message.content)
